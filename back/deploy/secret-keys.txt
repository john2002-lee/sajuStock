# Cloud Run 컨테이너에 바인딩할 Secret Manager 키 **이름** 목록. 단일 출처다.
#
# 이 파일에 값은 없다. 그리고 파일 이름이 `secrets.txt` 가 아닌 것도 그래서다 —
# 루트 `.gitignore` 의 `secrets.*` 규칙이 비밀 값 파일을 막고 있고, 그 규칙은 옳다.
# 이름을 예외로 뚫는 대신 이름을 정확하게 바꿨다. 여기에 **값을 적지 말 것** —
# 값은 Secret Manager 로만 간다 (`deploy.ps1`).
#
# 두 곳이 이 파일을 읽는다:
#   deploy.ps1                              — .env 의 값을 Secret Manager 로 올린다
#   .github/workflows/back-deploy.yml       — 배포할 때 KEY=KEY:latest 로 바인딩한다
#
# 목록을 두 곳에 적어 두면 새 비밀을 추가할 때 한쪽만 고치게 된다. 그리고 그 증상은
# 배포된 컨테이너에서만, 그것도 그 값을 처음 쓰는 요청에서만 나타난다 — 실제로
# AMPLITUDE_AI_API_KEY 가 그렇게 됐다(`.env`·`.env.example` 에는 있는데 Secret
# Manager 에는 없어서, 운영 백엔드만 조용히 Amplitude 없이 돌고 있었다).
#
# 규칙: 한 줄에 키 하나. `#` 뒤는 주석, 빈 줄은 무시.
#
# 여기 이름을 추가하는 것만으로는 배포에 반영되지 않는다 — **값** 을 올리는 것은
# `.env` 를 가진 로컬의 deploy.ps1 뿐이다. CI 는 Secret Manager 에 없는 키를
# 하드 실패로 만들지 않고(키 하나 때문에 배포 전체가 죽는다) 경고로 남긴다.
#

# 주소를 운영 컨테이너에 실어 보낼 이유가 없다.
