## 1. 한 줄 결론

**사주는 "이 종목이 오를까"가 아니라 "당신은 어떤 투자자인가"에 답한다.**
그렇게 얻은 성향 프로파일을 종목 판단과 결합해 **최종 매수·유지·매도 판단을 사람마다
다르게** 낸다. 판단이 사람마다 갈리는 것은 정당하다 — 금융의 적합성(suitability) 개념
그대로다 (3.2절).

지켜야 할 선은 두 개뿐이다.

1. **사주 원문은 판단 컨텍스트에 절대 들어가지 않는다.** 사주는 프로파일 초안까지만
   관여하고, 판단은 사용자가 확인한 숫자 프로파일만 본다 (5.2절)
2. **단방향 보정 원칙** — 프로파일은 판단을 보수적인 쪽으로만 움직인다. 절대 공격적으로
   밀지 않는다 (5.5절)

이 두 규칙을 코드로 강제하는 것이 이 문서의 핵심이다. 기술·심사·규제 세 방향에서 동시에
성립하는 유일한 지점이기 때문이다 (근거는 3절과 8절).

### 2.2 통합에 유리한 두 가지 사실

**(1) 에이전트가 이미 플러그인 구조다.**
[`prompts.py`](../back/app/agents/prompts.py)의 `ANALYST_PROFILES` 튜플이 사실상 레지스트리다.
프런트도 `AGENT_META`([`advice/model/types.ts`](../front/src/features/stock/advice/model/types.ts))에
한 줄 추가하면 카드가 그려진다. 다만 **사주를 여기 넣으면 안 된다** — 4절 참조.

**(2) 화면은 이미 "보유 중 판단"을 전제로 설계돼 있다.**
`WatchItem.verdict`가 `"비중 확대" | "유지" | "관망" | "과열 주의"`로 정의돼 있다
([`watchlist/model/types.ts`](../front/src/features/stock/watchlist/model/types.ts)).
반면 백엔드 `Verdict`는 `BUY | WATCH | AVOID`(= 사도 되나)뿐이다. 이 빈칸이 곧
"매도·유지 판단"이며, 6절에서 채운다.

### 2.3 통합의 실제 작업량

사주 엔진 연결 자체는 작다. **작업량의 대부분은 "사용자 소유 데이터 저장소가 통째로 없다"는
점에서 나온다** — 계정, 프로파일, 보유 종목, 분석 이력이 전부 신규다. 일정 산정 시
이쪽을 과소평가하면 안 된다.

## 3. 핵심 결정: 사주의 역할

### 3.1 정의

```
사주  →  투자자 성향 프로파일 (사람에 대한 정보)
데이터 →  종목 판단          (종목에 대한 정보)
둘의 결합 → 사람마다 다른 최종 매수·유지·매도 판단
```

같은 종목, 같은 데이터인데 최종 판단과 실행 가이드가 달라진다.

```
종목 판단: BUY · 변동성 32% · 신뢰도 74

A (위험선호 높음 / 인내심 높음)          적합도 81 → 최종 매수 검토
→ "분할로 담으세요. 변동성은 당신 감내 구간 안입니다."

B (손실회피 강함 / 결정속도 빠름)        적합도 38 → 최종 관망
→ "데이터는 매수 신호지만 당신에게는 맞지 않습니다.
   이 종목은 3개월간 -5%를 7번 지났고, 당신은 그 구간에서 던지는 유형입니다.
   그래도 사겠다면 평소의 1/3 수량, 손절선 -8% 선설정."
```

### 3.2 판단이 갈려도 되는 근거: 적합성(suitability)

같은 종목이 사람에 따라 다른 답을 갖는 것은 유사과학이 아니라 **금융의 표준 개념**이다.
변동성 32%, 5년 성장 스토리 종목은 위험선호·장기보유 투자자에게 정당한 매수이고,
손실회피·6개월 시계 투자자에게 정당한 회피다. 규제받는 투자자문사가 하는 일이 정확히
이 적합성 판단이다.

따라서 판단이 갈리는 것 자체는 방어할 필요가 없다. **갈리는 이유만 방어하면 된다.**

| 근거 | 방어 가능 여부 |
|---|---|
| "당신 사주에 화(火)가 강하니 매수" | 불가능 |
| "당신의 손실회피 성향(당신이 확인한)으로는 변동성 32%가 부담" | 적합성 판단으로 성립 |

이 차이가 5.2절의 프로파일 계약과 5.5절의 단방향 보정 원칙으로 코드에 박힌다.

### 3.3 이 방향을 택한 이유

| 이유 | 설명 |
|---|---|
| 심사 방어 가능 | 사주가 주가를 예측한다고 **주장하지 않는다**. "근거가 뭐냐"는 첫 질문에 답이 있다 |
| 실제 차별성 | 국내 증권 앱 중 "당신의 매매 습관에 맞춘 실행 가이드"를 하는 곳이 없다 |
| 규제 위험 최소 | 추천을 생성하지 않고 억제만 하는 구조다 (5.5절 · 8절) |
| 손실 클레임 차단 | 프로파일 경로는 언제나 더 보수적으로만 밀므로 "사주 때문에 손해봤다"가 구조적으로 성립하지 않는다 |
| 재미 요소 보존 | "오늘의 투자 운세"는 **판단과 분리된** 별도 영역으로 유지 |
| 양쪽 코드 100% 재사용 | 기존 판단 파이프라인을 하나도 안 버린다 |

### 3.4 가장 강한 제품 포인트: 온보딩 마찰 제거

증권사 투자성향 설문 20문항은 완주율이 낮다.

> **생년월일시 4개 입력 → 성향 프로파일 초안 자동 생성 → 사용자가 3번 탭해서 보정**

발표 첫 슬라이드가 이것이다. 부수 효과가 크다.

- 사주 해석이 틀려도 사용자가 고치므로 **제품이 깨지지 않는다**
- 최종 프로파일이 "사용자가 확인·수정한 자기 성향"이 되어 근거가 사용자에게 있다
- 콜드스타트(신규 사용자에 대해 아는 게 없는 상태)를 입력 4개로 통과한다

## 4. 하지 말 것 (안티패턴)

### 4.1 사주를 4번째 에이전트로 추가하기

가장 쉬운 길이다 (`ANALYST_PROFILES`에 항목 하나, 30분). 그리고 제품을 망친다.

- 의사결정 에이전트가 사주 의견을 **주가 근거와 동등하게** 종합한다 → 사주 때문에 매수
  판단이 실제로 바뀐다
- "사주가 주가를 예측한다는 근거는?"에 답할 수 없다
- 유료화 시 법적으로 가장 위험한 형태 (사주 기반 종목 추천의 판매)
- 사주의 강점(재미·개인화)은 못 쓰고 신뢰도만 깎인다

### 4.2 그 외

| 금지 | 이유 |
|---|---|
| 사주로 종목 자체를 추천 ("궁합 좋은 종목") | 재미로도 금지. 유료화 경로가 막힌다 |
| 백테스트로 사주 효과 증명 시도 | 증명 못 하고, 시도했다는 사실 자체가 약점이 된다 |
| 관심종목 일괄 분석을 무료로 개방 | 18종목 × LLM 4회. 비용이 즉시 터진다 |
| 사주 원문·오행·십성을 판단 LLM 컨텍스트에 투입 | 판단은 확인된 숫자 프로파일만 본다 (5.2) |
| 적합도로 판단을 공격적인 쪽으로 상향 | 단방향 보정 원칙 위반 (5.5) |
| 최종 판단 결합을 LLM에게 맡기기 | 재현·감사 불가능해진다. 결정론적 코드로 한다 (5.4) |
| 판단 영역과 운세 영역을 한 카드에 섞기 | 섞이는 순간 제품 전체가 오락으로 읽힌다 |

## 5. 아키텍처

### 5.1 데이터 흐름

```
[가입 1회]  생년월일시 → 사주엔진(동료) → InvestorProfile 초안 → 사용자 보정 → DB 영구 저장
                                                       ↓  (LLM 비용 0, 재계산 없음)
[종목 분석] 시세·지표·뉴스 → 에이전트 3인 → 의사결정 → ① MarketVerdict
                                                       │  (종목 단위, 전 사용자 공유, 캐시)
              InvestorProfile × StockMetrics ────────→ ② FitScore
                                                       │  (순수 함수, LLM 없음, 비용 0)
                                            ①+② ────→ ③ PersonalVerdict
                                                       │  (결정론적 규칙, LLM 없음)
                                                       ↓
                                          + 실행 가이드 (LLM 1회, 짧음)
```

핵심은 **사주 계산이 1회성**이라는 점이다. 생년월일시는 바뀌지 않으므로 영구 캐시가 가능하고,
운영 비용에 포함되지 않는다. 비싼 것은 종목 분석 쪽이며 7절에서 따로 다룬다.

### 5.2 프로파일 계약 — 가장 먼저 확정할 것

2인 병렬 작업의 성패가 여기서 갈린다. 이 스키마만 합의하면 동료가 사주 엔진을 만드는 동안
이쪽은 목 데이터로 전체 개발을 끝낼 수 있다.

```python
# back/app/schemas/profile.py  (신규)

class InvestorProfile(BaseModel):
    """사주 해석 또는 설문에서 도출한 투자 성향. 0~100 정규화."""

    risk_appetite: int          # 위험 감수도
    patience: int               # 보유기간 선호 (낮을수록 단타)
    decisiveness: int           # 결정 속도 (높을수록 충동적)
    loss_aversion: int          # 손실 회피 강도
    herd_tendency: int          # 군중 추종 성향

    source: Literal["saju", "survey", "user_edited"]
    saju_summary: str | None    # "화(火) 기운이 강해 결단이 빠른 편" — 재미 표시 전용
```

동료에게 요구하는 것은 **이 6개 값뿐**이다. 사주 → 숫자 매핑은 그쪽 도메인이다.

- 매핑 규칙은 **반드시 문서로 남긴다.** 심사에서 확실히 질문받는 항목이다
  (예: 오행 편중 → 결정 속도, 관성 → 손절 규율, 식상 → 성장주 선호)
- `saju_summary`는 화면 표시용 문장이며 **판단 계산에 절대 넣지 않는다**

### 5.3 통합 경계

```
back/app/integrations/saju/
├── __init__.py
├── client.py      ← 동료 엔진 호출 (라이브러리 import 또는 HTTP)
└── mapper.py      ← 엔진 응답 → InvestorProfile 변환
```

[`integrations/llm.py`](../back/app/integrations/llm.py)와 같은 패턴이다 — 경계 파일 하나로
격리해 두면 동료 코드가 파이썬 라이브러리든 별도 HTTP 서비스든, 나중에 바꿔도 앱이 흔들리지
않는다. 스택이 다르면 (Node/Java 등) HTTP로 부른다. 사주 계산은 순수 함수라 재시도·캐시가
자명하다.

**동료 진도와 무관하게 이쪽이 멈추지 않는 것이 이 경계의 목적이다.**

### 5.4 2축 판단 모델

최종 판단은 두 축을 결합해 만든다. **결합은 LLM이 아니라 결정론적 코드다.**

| 축 | 산출 | 사람 의존 | 비용 |
|---|---|---|---|
| ① `MarketVerdict` | 기존 에이전트 3인 + 의사결정 (현행 그대로) | 무관 | LLM 4회, 캐시됨 |
| ② `FitScore` | 프로파일 × `StockMetrics` — 순수 함수 | 의존 | 0 |
| ③ `PersonalVerdict` | ①②를 규칙으로 결합 | 의존 | 0 |

③을 LLM에 맡기지 않는 이유:

- **재현 가능** — 같은 입력이면 같은 출력. 심사 자리에서 다시 돌려 보일 수 있다
- **감사 가능** — "이 답이 왜 나왔나"에 정확한 규칙을 제시할 수 있다
- **단위 테스트 가능** — `domain/` 계층 규칙(네트워크·DB 없이 테스트)에 그대로 맞는다
- **비용 0** — LLM 호출이 늘지 않는다

"AI가 종합했습니다"보다 "이 부분은 결정론적이고 테스트로 검증됩니다"가 심사에서 강하다.

#### 적합도 계산 — 새 데이터가 필요 없다

[`StockMetrics`](../back/app/schemas/stock.py)에 필요한 종목 입력이 이미 전부 있다.

| 적합도 축 | 종목 입력 (이미 존재) | 프로파일 입력 |
|---|---|---|
| 변동성 부담 | `volatility_20d_pct` | `risk_appetite`, `loss_aversion` |
| 고점 추격 위험 | `week52_position_pct` | `herd_tendency` |
| 보유기간 정합 | `trend`, `recent_cross_signal` | `patience` |
| 진입 타이밍 규율 | `day_change_pct`, `volume_ratio_20d` | `decisiveness` |

```python
# back/app/domain/fit.py  (신규) — 순수 함수, LLM·네트워크 없음

class FitConcern(BaseModel):
    axis: str                                    # "변동성 부담"
    severity: Literal["low", "medium", "high"]
    message: str    # "변동성 32%는 당신의 감내 구간(약 21%)을 넘습니다"

class FitScore(BaseModel):
    score: int                    # 0~100
    concerns: list[FitConcern]

def compute_fit(profile: InvestorProfile, metrics: StockMetrics) -> FitScore:
    """예: 감내 변동성 = 10 + risk_appetite*0.3 - loss_aversion*0.15
    종목 변동성이 이를 넘으면 감점하고 concern 을 만든다."""
```

출력이 점수뿐 아니라 **축별 우려 문장**이라는 점이 중요하다. 화면에서 "왜 갈렸나"를
설명하는 재료가 여기서 나온다 (5.6절).

### 5.5 단방향 보정 원칙 — 가장 중요한 안전장치

> **적합도는 판단을 보수적인 방향으로만 움직인다. 절대 공격적으로 밀지 않는다.**

```python
# back/app/domain/verdict.py  (신규)
def combine(market: MarketVerdict, fit: FitScore) -> PersonalVerdict: ...
```

|  | 적합도 높음 | 적합도 보통 | 적합도 낮음 |
|---|---|---|---|
| `BUY` | 매수 검토 | 분할 매수 | **관망** |
| `WATCH` | 관망 | 관망 | 비대상 |
| `AVOID` | 매수 보류 | 매수 보류 | 매수 보류 |
| `ADD` (보유) | 비중 확대 | 유지 | **일부 익절** |
| `HOLD` (보유) | 유지 | 유지 | **비중 축소 검토** |
| `TRIM` (보유) | 일부 익절 | 일부 익절 | 정리 검토 |
| `EXIT` (보유) | 정리 | 정리 | 정리 |

세로로 읽으면 규칙이 보인다 — **적합도가 아무리 높아도 `AVOID`가 `BUY`로 올라가지 않는다.**
프로파일은 브레이크지 액셀이 아니다.

이 한 줄이 지키는 것:

| 위험 | 해소 방식 |
|---|---|
| "사주가 매수를 추천하나요?" (심사) | "아니요. 프로파일은 매수를 만들어내지 못합니다. 보류시킬 수만 있습니다" |
| 투자 추천 규제 | 추천을 생성하지 않고 억제만 하는 구조 |
| "사주 때문에 손해봤다" 클레임 | 프로파일 경로는 언제나 더 보수적으로만 밀었으므로 구조적으로 성립 불가 |
| 제품 가치 훼손 | 그럼에도 최종 판단은 사람마다 다르다 — 핵심 가치는 유지된다 |

이 규칙은 `combine()`의 단위 테스트로 강제한다. "어떤 입력으로도 판단이 상향되지 않는다"를
성질 테스트(property test)로 두면 이후 누가 고쳐도 원칙이 깨지지 않는다.

### 5.6 불일치 화면 — 제품에서 가장 중요한 화면

2축이 생기면 둘이 엇갈리는 경우가 나온다. 숨기지 말고 이것을 메인으로 삼는다.

```
시장 판단   BUY  · 신뢰도 74      ← 데이터는 사라고 말합니다
당신 적합도  38 / 100             ← 당신에게는 맞지 않습니다
──────────────────────────────
최종        관망

왜 갈렸나                          ← FitScore.concerns 에서 생성
· 20일 변동성 32% — 당신 감내 구간 21% 초과
· 당신은 -5% 구간에서 매도하는 유형입니다.
  이 종목은 지난 3개월간 -5%를 7번 지났습니다.

그래도 사겠다면                    ← 막지 않고 방법을 준다
· 평소의 1/3 수량으로 시작
· 손절선 -8% 미리 설정
```

마지막 블록이 핵심이다. **막지 않고 어떻게 하면 되는지를 준다.** "AI가 종목을 추천"과
결정적으로 다른 지점이고, 대회에서 기억에 남는 화면이다.

### 5.7 화면 규칙

사주 원문이 화면 어디까지 나오는지를 고정한다. 이 경계가 흐려지면 3.2절의 방어 논리가
무너진다.

| 항목 | 노출 위치 |
|---|---|
| 사주 원문 · 오행 · 십성 | 프로파일 화면의 **"왜 이 성향이 나왔나"** 설명에만 |
| 판단 화면 | "당신의 성향: 손실회피 높음"까지. 사주 언급 없음 (원할 때만 토글) |
| 판단 LLM 컨텍스트 | 사주 텍스트 투입 금지. `InvestorProfile` 숫자만 |
| 운세 · 재미 | 완전 분리된 카드. 판단에 영향 없음 |

그 외:

- 판단 영역과 재미 영역을 **시각적으로 완전히 분리**한다. "오늘의 투자 운세"는 다른 색,
  다른 카드, 명시적 라벨
- 프로파일 화면에 "이 분석은 사주 해석 기반 초안이며, 직접 수정하실 수 있습니다"를 명시한다.
  정직함이 방어막이다
- 기존 고지 문구([`decision.py`](../back/app/agents/decision.py)의 "투자 손익을 보장하지
  않는 참고 의견")는 유지한다

## 6. 매도 · 유지 판단 축 추가

현재 백엔드는 "사도 되나"만 답한다. 사용자가 원하는 매도·유지를 채우려면 판단 축이 하나 더
필요하다. 화면 타입은 이미 이를 전제하고 있다 (2.2절).

### 6.1 요청 스키마 확장

```python
# back/app/schemas/advice.py

class Position(BaseModel):
    quantity: float
    avg_price: float
    bought_at: date | None = None

class StockAdviceRequest(BaseModel):
    symbol: str = Field(min_length=1, max_length=80)
    position: Position | None = None   # 신규 — 있으면 보유자 판단으로 분기
```

### 6.2 판단 축

여기서 나오는 것은 5.4절의 ① `MarketVerdict`다. 최종 판단은 `FitScore`와 결합한 뒤 나온다.

| 상태 | MarketVerdict |
|---|---|
| 미보유 (`position is None`) | `BUY` 매수 가능 / `WATCH` 관망 / `AVOID` 매수 보류 — 현행 유지 |
| 보유 중 (`position` 있음) | `ADD` 비중확대 / `HOLD` 유지 / `TRIM` 일부 익절 / `EXIT` 정리 |

결합 규칙은 5.5절 표에 두 상태가 모두 들어 있다. 보유 중일 때도 단방향 보정은 동일하다 —
적합도가 낮으면 `HOLD`가 `비중 축소 검토`로 내려가지만, 적합도가 높다고 `TRIM`이 `ADD`로
올라가지는 않는다.

### 6.3 프로파일과의 접점

보유자 판단은 입력이 하나 늘어난다 — **평단 대비 수익률**. 이것이 프로파일과 궁합이 좋다.

- `loss_aversion`이 높은 사용자의 -12%와 낮은 사용자의 -12%는 다른 조언이 나가야 한다
- `patience`가 낮은 사용자에게는 "지금 팔고 싶어지는 게 정상"이라는 메타 인지를 준다
- 미실현 손실 구간에서는 `FitScore`의 우려 문장이 특히 값을 낸다 (손절 규율)

에이전트 프롬프트는 [`prompts.py`](../back/app/agents/prompts.py) 한곳에 모여 있으므로
보유자용 분기만 추가하면 된다.

## 7. 비용 · 지연 구조 (수익화의 실제 병목)

### 7.1 현재 문제

지금은 **사용자 1명이 한 종목을 분석할 때마다 opus-5를 4회 호출**한다
(에이전트 3 + 의사결정 1). 100명이 같은 종목을 보면 400회다. 이 구조로는 유료화가 불가능하다.

### 7.2 (a) 2단 분리 — 가장 큰 개선

종목 분석 결과는 사용자와 무관하므로 공유·캐시할 수 있다.

| 계층 | 단위 | 비용 |
|---|---|---|
| `BaseAnalysis` | 종목 × 날짜 | LLM 4회, 하루 1회, 전 사용자 공유 |
| `PersonalGuide` | 사용자 × 종목 | LLM 1회, 짧은 프롬프트 |

비용이 **사용자 수가 아니라 종목 수에 비례**하게 된다. 규모에 따라 10~100배 차이다.

### 7.3 (b) 모델 티어링

[`core/config.py`](../back/app/core/config.py)에서 `anthropic_model`이 전역 하나로 고정돼 있다.
하위 에이전트 3인과 최종 판단을 분리한다.

- 하위 에이전트 3인 → sonnet
- 최종 판단 (구조화 출력) → opus

`AgentProfile`([`prompts.py`](../back/app/agents/prompts.py))에 `model` 필드 하나를 추가하면 된다.

### 7.4 (c) 인기 종목 사전 생성

시총 상위 200종목을 장 마감 후 배치로 미리 돌려둔다. 사용자 체감은 즉시 응답이 되고 비용은
예측 가능해진다. [`main.py`](../back/app/main.py)의 `_warm_up()` 배경 작업 패턴이 이미 있으므로
같은 자리에 붙인다.

### 7.5 무료 / 유료 경계 (초안)

| 구분 | 범위 |
|---|---|
| 무료 | 시장 현황, 종목 조회, 사주 프로파일 1회 생성, 하루 AI 분석 3회 |
| 유료 | 분석 무제한, 관심종목 일괄 분석, 보유 기반 매도/유지 판단, 알림, 분석 이력 비교 |

## 8. 규제 · 라이선스 확인 항목

대회 출품 자체는 문제가 되지 않는다. **유료화하는 순간 성격이 달라진다.**

### 8.1 확인이 필요한 사항

- 자본시장법상 **투자자문업은 금융위 등록** 대상이다. "특정 개인에게 맞춘 투자 조언"은
  여기에 가까워진다
- **유사투자자문업**(불특정 다수 대상 유료 투자정보 제공)은 신고 대상이며, 최근 수년간
  규제가 강화되는 방향이었다
- **데이터 라이선스**: yfinance는 Yahoo 비공식 스크래핑이라 상업적 이용 조건이 불명확하다.
  유료 서비스로 갈 경우 KRX 정보데이터시스템 또는 증권사 API로 갈아탈 경로를 미리 확보한다
- 지연 시세 표시 의무, 재배포 가능 범위

### 8.2 기억할 역설

**개인화가 강해질수록 규제 위험이 커진다.**

- "당신에게 이 종목을 추천합니다" → 위험
- "당신은 이런 유형이니 이 정보를 이렇게 해석하세요" → 상대적으로 안전

3절의 방향(사주 = 성향 프로파일, 판단 = 데이터)이 이 이유로도 유리하다.

### 8.3 주의

정확한 판단 기준은 법무 확인이 필요하다. 이 문서의 역할은 **확인 항목을 빠뜨리지 않는 것**까지다.
고지 문구 하나로 해소되는 문제가 아니다.

- [`lib/config/env.ts`](../front/src/lib/config/env.ts)의 `USE_MOCK` 플래그를 **절대 지우지

- 시연 종목은 미리 분석해 캐시에 넣어둔다. 무대에서 40초 로딩은 치명적이다
- SSE 단계별 진행 표시는 큰 자산이다 — "AI가 생각하는 과정"이 보이는 데모는 심사에서
  효과가 크다

### 10.3 신뢰 설계

- 판단 영역과 운세 영역의 시각적 분리 (5.5절)
- 프로파일이 초안이며 수정 가능함을 명시

| 사주 → 6개 축 매핑의 구체 규칙 | 0주차, 동료 작성 |
| 대회 우선 vs 수익화 우선 (규제 대응 강도가 달라진다) | 1주차 |
| 유료 전환 시 데이터 공급자 교체 대상 | 수익화 결정 후 |
| 프로파일 재산정 허용 여부 (사용자가 수정한 뒤 되돌리기) | 1주차 온보딩 설계 시 |
