## 지금 상태 한눈에 (2026-08-07 기준 · 16회차까지 반영)

### ✅ 5회차부터 막혀 있던 것 — 10회차에서 전부 뚫렸다

AI 판단이 **처음으로 끝까지** 돌았다. 3 에이전트 전부 `status=done`, `decision_source=llm`,
RAG 근거 문서까지 실제로 인용된다.

| 막혀 있던 것 | 지금 |
|---|---|
| OpenAI 키가 401 (5~9회차 내내) | **Gemini 로 교체**해 해결 (10회차) |
| Supabase 미연결 → Postgres SQL 경로 미검증 | 풀러 주소로 연결, `verify_rag` 5단계 전부 통과 |
| RAG 실데이터 E2E 미확인 | 색인 4청크 → 하이브리드 검색 6건 → 판단이 D1·D2·D3 인용 |

> `.env`를 고쳐도 **서버는 안 읽는다** — `settings`는 프로세스 기동 시 1회만 만들어지고
> uvicorn 리로더는 `*.py`만 감시한다. 고친 뒤 반드시 `back/`에서 재시작한다
> (`env_file=".env"`가 CWD 기준이다).

### AI 토큰을 쓰는 곳 — 여기만 돈이 나간다

**앱 전체에서 LLM SDK를 import하는 파일은 [`llm.py`](../back/app/integrations/llm.py) 하나뿐이다.**
의도적인 설계이고, 그래서 프로바이더 교체가 파일 하나로 끝난다.
현재 프로바이더는 **Google Gemini** 다 (2회차 Anthropic→OpenAI, 10회차 OpenAI→Gemini).

```
llm.py  ask_structured → agents/analysts.py   에이전트 3인 (병렬, 5회차부터 구조화)
                       → agents/decision.py   최종 판단 1회
        embed_texts   → services/rag_service.py  색인·검색 (5회차 신설)
                              ↓
        services/advice_service.py    일괄 응답
        services/advice_stream.py     SSE 4단계
                              ↓
        POST /api/v1/stocks/advice
        POST /api/v1/stocks/advice/stream
```

**종목 1개 분석 = LLM 4회 + 임베딩 1~N회** (AI 저널리스트 · AI 경제학자 · AI 애널리스트 병렬 +
AI 의사결정자, 여기에 새 뉴스가 있을 때만 임베딩이 추가된다 — 이미 색인된 기사는 건너뛴다).

| 토큰을 쓰는 것 | 토큰을 안 쓰는 것 (전부 yfinance·KRX) |
|---|---|
| `POST /stocks/advice` | `/markets/overview` · `/markets/movers` |
| `POST /stocks/advice/stream` | `/stocks/history` · `/stocks/content` · `/stocks/fundamentals` |
| RAG 임베딩 (색인 시 새 문서만 · 검색 시 질의 1회) | `/stocks/suggestions` · `/stocks/listed-companies` · `/health` |

프런트 진입점: [`api/stocks/advice/route.ts`](../front/src/app/api/stocks/advice/route.ts)(BFF) →
[`useAiAdvice`](../front/src/features/stock/advice/hooks/useAiAdvice.ts)(1종목) ·
[`useBulkAdvice`](../front/src/features/stock/advice/hooks/useBulkAdvice.ts)(관심종목 일괄).
아침 브리핑(`MorningBriefing`)은 목 데이터라 토큰을 쓰지 않는다.

### ✅ AI 토큰 안전장치 (7회차에서 셋 다 처리)

유료 키를 붙이면 실제 비용 위험이 되는 셋이었다. 전부 걸었다 — 자세한 근거는 7회차.

| 위험 | 지금 | 수도꼭지 |
|---|---|---|
| 일괄 분석 총량 무제한 (20종목 = 80회) | 캐시 적중분을 먼저 채우고 **남은 것만 10종목** | `MAX_BULK_SYMBOLS` |
| 새로고침마다 4회 재소모 | **2층 캐시** — TTL 안엔 뉴스 조회도 없고, 만료 뒤엔 기사 지문이 같으면 LLM 0회 | `ADVICE_CACHE_TTL_SECONDS` |
| `/stocks/advice` 무인증 공개 | **공유 비밀키 헤더**(`X-Advice-Key`). 프런트 BFF만 알고 브라우저엔 안 나간다 | `ADVICE_API_KEY` |

> **`ADVICE_API_KEY`를 비우면 인증이 꺼진다** (로컬 개발 기본값). 그 상태로 외부에
> 노출하면 예전과 똑같으므로, 꺼져 있으면 기동 로그가 매번 경고한다. 배포 전에
> `back/.env`와 `front/.env.local`에 **같은 값**을 넣어야 한다.

남은 비용 관련 미결: 사용자별 한도·과금은 로그인이 필요하므로 P2(관심종목 실데이터화)와 함께 간다.

## 1회차 — 2026-08-04 · 재무·밸류에이션 기능 추가

### 왜 했나

"주식에 관심 있는 사람들이 뭘 보는지" 조사한 결과, 개인 투자자의 관심은
**수급 · 배당 · 실적 · 밸류에이션**에 몰려 있었다. 반면 이 서비스는 "차트 + AI 코멘트"만 있고
상위 관심사 6개 중 5개가 없었다. 그중 **밸류에이션과 배당**은 이미 설치된 `yfinance` 하나로
전부 조달되므로 투입 대비 회수가 가장 좋다고 판단해 먼저 했다.

부수적으로 AI 에이전트가 기술적 지표(SMA·볼린저)만 보고 판단하는 문제도 있었다 —
"PER 176배인데 BUY"가 나올 수 있는 구조였다.

### 무엇이 생겼나

1. **`GET /api/v1/stocks/fundamentals`** — PER·PBR·EPS·BPS·ROE·시가총액·배당수익률·주당배당금·
   배당락일·다음 실적발표일 + 연간 매출/영업이익 4개년. 종목당 15분 TTL 캐시(심볼별 락).
2. **재무 탭이 실데이터로 채워짐** — 전에는 "재무 화면은 아직 설계되지 않았습니다"만 뜨던 빈 껍데기였다.
3. **우측 레일에 밸류에이션 3행 상시 노출** (`ValuationRail`) — 재무는 세 번째 탭이라 기본으로
   가려지는데, "지금 비싼가/얼마 주나"는 클릭 없이 보여야 하는 축이라 요약을 따로 뺐다.
4. **AI 판단이 밸류에이션을 봄** — `build_context`(에이전트 3인)와 `decide`(최종 판단) 양쪽에 주입.

### 반드시 기억해야 할 함정 3개 (실측으로 확인)

계획 단계에서 세운 가정 중 셋이 실제 호출로 뒤집혔다. **직관과 반대라 다음에 또 밟는다.**

| # | 함정 | 실측 근거 |
|---|---|---|
| 1 | **국내 종목은 `info["trailingPE"]`가 항상 `None`** | 005930.KS · 000660.KS · 247540.KQ 전부 `None`, AAPL만 34.84. `get_valuation_measures()`가 유일한 경로이고 **yfinance ≥ 1.5**에만 있다 |
| 2 | **`dividendYield`는 이미 백분율, `returnOnEquity`는 소수** | 같은 dict인데 규약이 반대. 삼성전자 `dividendYield=0.57`(= 0.57%), `returnOnEquity=0.30792`(→ ×100 = 30.79%) |

## 2회차 — 2026-08-04 · LLM 프로바이더 Anthropic → OpenAI 교체

### 왜 했나

OpenAI(GPT) API 키를 확보해서 프로바이더를 옮겼다.

### 무엇이 바뀌었나

**바뀐 것은 [`llm.py`](../back/app/integrations/llm.py) 한 파일과 설정 4줄뿐이다.**
에이전트·서비스·엔드포인트 코드는 한 줄도 안 건드렸다 — `ask_text`/`ask_structured`
두 함수로 경계를 잡아둔 설계가 실제로 값을 한 번 했다.

| 항목 | 전 (Anthropic) | 후 (OpenAI) |
|---|---|---|
| SDK | `AsyncAnthropic` | `AsyncOpenAI` |
| API | Messages | **Responses** |
| 자유 서술 | `beta.messages.create` | `responses.create` |
| 구조화 출력 | `beta.messages.parse(output_format=)` | `responses.parse(text_format=)` |
| 시스템 프롬프트 | `system=` | `instructions=` |
| 토큰 상한 | `max_tokens=` | `max_output_tokens=` |
| 추론 강도 | `thinking` + `output_config.effort` | `reasoning={"effort": ...}` |
| 거절 감지 | `stop_reason == "refusal"` | 출력 블록의 `content.type == "refusal"` |
| 설정 | `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` | `OPENAI_API_KEY` / `OPENAI_MODEL` |
| 기본 모델 | `claude-opus-5` | `gpt-5.4` |

**없어진 설정**: `LLM_SERVER_SIDE_FALLBACK` — Anthropic 전용 베타(거절 시 서버 측 대체 모델
재실행)라 대응 개념이 없다. 없어도 앱은 규칙 기반으로 자체 폴백하므로 기능 손실은 없다.

**그대로인 설정**: `LLM_MAX_TOKENS` · `LLM_EFFORT` · `LLM_TIMEOUT_SECONDS` · `LLM_MAX_RETRIES`.
`llm_effort`의 값(`low`~`max`)이 OpenAI `reasoning.effort`와 그대로 맞아떨어져 운이 좋았다.

의존성에서 `anthropic`을 제거했다. `openai`는 원래 "설치만 되고 안 쓰는 의존성"이었는데
이제 실제로 쓴다.

### 새로 생긴 주의점

- **`LLM_EFFORT`는 gpt-5 계열·o 시리즈에서만 유효하다.** 비추론 모델을 `OPENAI_MODEL`에 넣으면
  `reasoning` 파라미터에서 400이 날 수 있다.
- **추론 토큰도 `LLM_MAX_TOKENS`를 함께 먹는다.** 이 값이 낮으면 본문이 빈 채로 `status=incomplete`가
  된다. 그대로 두면 상위에 "빈 응답"으로만 보여 원인을 못 찾으므로 `_guard()`에서 WARNING을 남긴다.
- **키가 없으면 클라이언트 생성 시점에 바로 예외가 난다.** Anthropic SDK는 호출 시점까지 미뤘다.
  다만 `get_client()`가 `ask_*` 안에서 지연 호출되고 에이전트 계층이 예외를 잡으므로,
  **동작은 전과 같다** — 200 응답 + `agents[*].status="fallback"` + `decision_source="fallback"`.
  (검증함)

### 키 넣는 법

`back/.env`는 gitignore돼 있고 지금 **파일 자체가 없다.** 만들어야 한다:

```bash
cd back
cp .env.example .env
# .env 를 열어 OPENAI_API_KEY=sk-... 를 채운다
```

넣은 뒤 라이브 검증:

```bash
uv run python -m scripts.verify_llm
```

3단계가 독립적으로 실패 원인을 좁힌다: ① 자격 증명·모델 접근 → ② `ask_text` 요청 형태 →
③ `ask_structured` 구조화 출력. 통과하면 실제 엔드포인트에서 `agents[*].status`가 전부
`"done"`인지 확인한다 — `"fallback"`이면 LLM이 아니라 규칙 기반으로 답한 것이다.

### 검증

`ruff` 통과, 테스트 97개 전부 통과. 키 없는 상태에서 3에이전트 → `fallback`,
최종 판단 → 규칙 기반으로 정상 degrade 확인 (예외가 밖으로 새지 않음).

**아직 못 한 것**: 실제 키로 네트워크 왕복을 돌려보지 않았다. `.env`에 키를 넣고

## 5회차 — 2026-08-04 · AI 판단 실패 원인 규명 + RAG 1단계

### 5-1. "키를 넣었는데 AI가 거절된다" — 원인 두 개

Supabase 미연결이 원인일 것이라는 가설이 있었으나 **아니었다.** 실측으로 원인 둘을 분리했다.

**원인 ① 실행 중인 서버에 키가 없었다.**

BFF로 실제 스트림을 받아보니 세 에이전트 전부 `Missing credentials ... set the OPENAI_API_KEY`였다.
시각을 대보면 명확하다.

| | 시각 |
|---|---|
| 백엔드 프로세스 기동 | 21:58:45 |
| `back/.env` 마지막 수정 | **22:16:10** |

**서버가 떠 있는 상태에서 키를 추가**했고, `settings`는 import 시점 1회만 만들어지며 uvicorn
리로더는 `*.py`만 감시한다 → `.env`를 고쳐도 재시작되지 않는다. **재시작이 필요하고,
`env_file=".env"`가 CWD 기준이라 반드시 `back/`에서 띄워야 한다.**

**원인 ② 그 키 자체가 OpenAI에서 거부된다.**

앱을 거치지 않고 `.env`의 키만으로 `https://api.openai.com/v1/models`에 직접 요청 →
**401 `invalid_api_key`**. 형식은 정상(164자, `sk-proj-`, 공백·따옴표·비ASCII 없음),
OS 환경변수 충돌 없음, DNS·TCP 443 정상, 프록시 없음. 403(권한)이 아니라 401(모르는 키)이라
폐기됐거나 다른 계정/프로젝트의 키다. **재시작만으로는 안 되고 키를 갈아야 한다.**

**Supabase가 아닌 근거**: 코드 전체에 `supabase` 참조 0건, `DATABASE_URL`은 로컬 SQLite이고
정상 동작 중(검색·랭킹이 뜬다), 무엇보다 401은 DB를 거치지 않는 경로에서 났다.
AI 판단 경로는 DB를 읽지 않는다 — yfinance + OpenAI뿐이다.

**진단이 어려웠던 이유도 고쳤다.** LLM 실패는 전부 폴백으로 흡수되어 화면에는 "실패" 배지만
남고 원인 문자열은 SSE에만 실려 있었다. 5-2에서 근거·성향을 화면에 올리면서 이 사각지대도 줄었다.

### 5-2. RAG 1단계 — Supabase pgvector + 하이브리드 검색

**결정 사항** (선택지 검토 후): 벡터 스토어는 **Supabase pgvector**, 그래프 런타임은
**LangGraph**(2단계로 미룸), 이번 범위는 **1단계 RAG 기반**까지.

**왜 했나** — 에이전트가 받던 문서가 "가장 최근 뉴스 3건"이었다. 최신순은 관련성과 무관해서
지수 편입 공지나 배당 기준일 안내가 실적 악화 기사보다 앞자리를 차지한다.

```
수집(yfinance) → 청킹 → 임베딩 → pgvector 적재
                                      ↓
질의 ──┬─ 벡터 검색(의미)   ─┐
       └─ 키워드 검색(어휘) ─┴─ RRF 융합 → 상위 K → 프롬프트 + 인용
```

**새 파일**

| 파일 | 역할 |
|---|---|
| [`services/rag_service.py`](../back/app/services/rag_service.py) | 색인·검색·RRF 융합. 실패를 전부 흡수하는 경계 |
| [`repositories/document_chunk.py`](../back/app/repositories/document_chunk.py) | pgvector 원시 SQL. 멱등 `ensure_schema` + HNSW·트라이그램 인덱스 |
| [`core/vector_database.py`](../back/app/core/vector_database.py) | 주 DB와 분리된 엔진 + Supabase URI 정규화 |
| [`domain/chunking.py`](../back/app/domain/chunking.py) | 문단→문장 경계 분할 (순수 함수) |
| [`scripts/verify_rag.py`](../back/scripts/verify_rag.py) | 5단계 라이브 검증 **겸 최초 스키마 부트스트랩** |
| [`tests/test_rag.py`](../back/tests/test_rag.py) · [`test_advice_stream.py`](../back/tests/test_advice_stream.py) | 13 + 5개 |

**설계에서 지킨 것**

- **두 검색기를 함께 쓴다.** 벡터는 "실적 부진"과 "어닝 쇼크"를 묶지만 종목코드·수치에 약하고,
  트라이그램은 그 반대다. 점수 스케일이 전혀 다르므로(코사인 거리 vs 트라이그램 유사도)
  정규화해 더하지 않고 **순위만 쓰는 RRF**로 합친다 — 스케일 가정이 코드에 스며들지 않는다.
- **키워드 검색은 `word_similarity`(`<%`)를 쓴다.** 일반 `similarity()`는 짧은 질의와 긴 본문을
  통째로 비교해 항상 낮게 나온다. 한국어라 형태소 사전이 필요한 `tsquery`보다 트라이그램이 안전하다.
- **벡터 DB는 주 DB와 엔진을 분리한다.** 로컬 주 DB가 SQLite라 `vector` 확장을 못 올리고,
  같은 `Base.metadata`에 얹으면 개발용 `create_all()`이 깨진다.
- **인용을 검증한다.** 에이전트는 `cited_doc_ids`로 doc_id를 돌려주고
  [`resolve_sources()`](../back/app/agents/analysts.py)가 **실제 검색 결과에 없는 ID는 버린다.**
  모델이 `D9`를 지어내는 일이 있는데, 없는 출처가 "근거"로 뜨는 건 근거가 없는 것보다 나쁘다.
- **RAG 실패 ≠ 판단 실패.** 미설정·연결 실패·타임아웃 전부 빈 목록으로 흡수되고, 그때는
  프롬프트의 근거 규칙이 "문서가 없으면 뉴스를 언급하지 마라"로 작동한다.
- **재임베딩을 건너뛴다.** `doc_key`(URL 해시)로 이미 색인된 기사를 판별한다. 안 하면 같은 기사
  임베딩 비용이 요청 수에 비례한다.

**곁다리로 채워진 것** — 하위 에이전트를 `ask_text` → `ask_structured`(`AnalystOutput`)로 바꾸면서
프런트가 오래 비워 두고 있던 **`stance`(긍정·중립·부정 배지)와 근거 목록**이 채워졌다.
`screen-spec.md`의 미구현 항목 O-02가 해소돼 목록에서 뺐다.

## 7회차 — 2026-08-05 · AI 토큰 안전장치 3종 (P1.5)

### 왜 지금 했나 — 순서를 바꿨다

문서상 P1.5였지만 P0(RAG 2단계)보다 **먼저** 했다. P0의 전제인 유효한 OpenAI 키가
아직 없는데, 그 키를 꽂는 순간 아래 셋이 전부 실제 비용으로 바뀌기 때문이다.

- 관심종목 20개 → '전체 AI 분석' 버튼 한 번 = **LLM 80회**
- 같은 종목 새로고침마다 4회 재소모
- `/stocks/advice` 무인증 공개

안전장치를 키보다 먼저 다는 것이 맞다. 셋 다 **토큰을 한 푼도 쓰지 않고** 개발·검증된다.

### ① 결과 캐시 — 왜 단순 TTL 이 아닌가

TTL 하나로는 두 요구가 충돌한다.

| TTL | 문제 |
|---|---|
| 짧게 (1분) | 비용이 거의 안 준다 |
| 길게 (1시간) | **악재 기사가 떠도 한 시간 동안 낡은 BUY 판단**을 보여준다. 투자 판단에서 이건 캐시가 아니라 오보다 |

그래서 시간이 아니라 **입력이 바뀌었는지**로 무효화한다. 이 판단의 입력 중 자주 바뀌는
것은 뉴스·리포트뿐이다(주가는 판단을 뒤집을 만큼 안 움직이고 재무는 분기 단위).
그 목록의 **지문**을 캐시 키에 함께 넣는다.

지문 확인에도 유예를 둔 것은 뉴스 조회가 이 경로 응답 시간의 대부분(측정치 95%)이기
때문이다. 매번 확인하면 LLM 은 아껴도 화면은 여전히 느리다.

```
요청 ─▶ ① TTL(600초) 안인가?
           예   → 캐시 반환. 네트워크 0회, LLM 0회
           아니오 ↓
        ② 뉴스를 조회해 지문 비교
           같다   → 캐시 반환 + 수명 연장(checked_at 갱신). LLM 0회
           다르다 → 다시 분석. LLM 4회
```

②에서 지문이 같으면 수명만 늘린다 — "기사가 그대로면 판단도 그대로"를 명시적으로
쓴 것이고, 덕분에 **조용한 종목은 하루 종일 LLM 을 한 번도 더 쓰지 않는다.**

클라이언트(React Query)는 그 위에 한 층 더 얹는다. `staleTime` 을 서버 TTL 과 같은
10분으로 두어 그 안에는 요청 자체가 나가지 않는다. 두 층이 아끼는 것이 다르다 —
클라이언트는 네트워크 왕복을, 서버는 LLM 4회를 아낀다.

**클라이언트는 "새 기사가 떴는지" 를 판단하지 않는다.** 그건 뉴스 목록을 쥔 서버만
알 수 있다. staleTime 이 지나면 그냥 다시 물어보고, 새 기사가 없으면 서버가 LLM 없이
즉시 같은 답을 준다.

### ② 총량 상한 — 대기가 아니라 거절

| 층 | 값 | 동작 |
|---|---|---|
| 프런트 일괄 | `MAX_BULK_SYMBOLS=10` | 캐시 적중분을 먼저 채우고 **남은 것에만** 상한 |
| 프런트 동시 | `MAX_CONCURRENT=3` (기존) | 그대로 |
| 백엔드 동시 | `ADVICE_MAX_CONCURRENT=4` | 초과 시 **429 + Retry-After** |

`asyncio.Semaphore` 를 쓰지 않았다. 세마포어의 `async with` 는 자리가 날 때까지
**기다린다** — 그러면 상한이 아니라 큐가 되고 LLM 호출 총량은 한 푼도 안 줄어든다.
늦게 나가는 것과 안 나가는 것은 비용 관점에서 완전히 다르다. `locked()` 로 보고
`acquire()` 하는 방법도 안 된다: 둘 사이에 `await` 가 있어 마지막 자리를 다른 코루틴이
채가면 거절하려던 요청이 대기로 빠진다. 정수 카운터는 검사와 증가 사이에 `await` 가
없어 asyncio 단일 스레드에서 원자적이다.

스트리밍은 슬롯을 **응답 헤더가 나가기 전에** 잡는다. 제너레이터 안에서 잡으면 거절을
알릴 때 이미 `200 text/event-stream` 이 나간 뒤라 클라이언트가 **거절인지 장애인지
구분할 수 없다.** 그리고 소비자가 중간에 끊어도(GeneratorExit) `finally` 로 반드시
반납한다 — 안 그러면 드로어를 몇 번 여닫는 것만으로 상한이 영구히 찬다.

캐시 적중분을 상한보다 **먼저** 채우는 순서도 의도다. 캐시 적중이 상한을 잡아먹으면
방금 본 종목 때문에 새 종목이 밀려나는 이상한 동작이 된다. 잘린 수는 `skipped` 로
돌려받아 화면이 밝힌다 — 20개를 골랐는데 10개만 도는 것을 말없이 하면 버그로 읽힌다.

### ③ 인증 — 로그인이 아니라 공유 비밀키

제대로 된 답은 사용자 인증이지만 그건 `auth.ts` 가 `providers: []` 인 지금 상태에서
P2(관심종목 실데이터화)를 통째로 끌고 들어온다. 반면 지금 막아야 하는 위협은 **"외부에서
남이 우리 토큰을 태우는 것"** 하나이고, 여기에는 프런트 BFF 만 아는 키로 충분하다.
이 프로젝트는 이미 "브라우저는 FastAPI 를 직접 호출하지 않는다"(CONVENTIONS)는 규칙이
있어 키를 실을 자리가 서버 한 곳으로 이미 좁혀져 있었다.

```
브라우저 ──(키 없음)──▶ Next BFF ──(X-Advice-Key)──▶ FastAPI
                          └ 키는 서버 측 env 에만 있다
```

- **토큰을 쓰는 두 경로만 잠근다.** `/markets/*` · `/stocks/history` · `/stocks/suggestions`
  는 yfinance·KRX 결과라 남이 불러도 우리 토큰이 줄지 않는다. 전부 잠그면 프런트 서버
  컴포넌트의 모든 호출에 키를 실어야 하고, **키가 닿는 표면이 넓어질수록 새어나갈 곳도
  많아진다.**
- **`==` 가 아니라 `secrets.compare_digest`.** 문자열 비교는 첫 불일치에서 빠져나와 응답
  시간에 "앞 몇 글자가 맞았는지"가 실린다. 네트워크 지터에 묻히긴 하지만 비밀을
  비교하는 자리에서 굳이 그 논쟁을 남길 이유가 없다.
- **미제출인지 오유인지 응답에 싣지 않는다.** 구분해 주면 헤더 이름을 모르는 사람에게
  그것부터 알려주는 셈이다.
- **미설정이면 열려 있다.** 그렇지 않으면 이 자물쇠가 "개발 시작 전에 먼저 풀어야 하는
  것"이 되어 결국 아무도 켜지 않는다. 대신 꺼져 있으면 기동 로그가 매번 경고한다 —
  **조용히 열려 있는 것이 가장 나쁘다.**

나중에 사용자별 한도·과금이 필요해지면 `require_advice_key` 를 세션 검사로 바꾸면 되고
엔드포인트는 손대지 않아도 된다.

### 이번에 알게 된 것

| 발견 | 내용 |
|---|---|
| **인증 테스트가 네트워크를 쳤다** | 키가 맞는 경로가 자물쇠를 통과한 뒤 실제 yfinance·LLM 까지 내려가 10개 테스트에 **18.8초**가 걸렸다. 서비스 경계를 대역으로 세워 0.33초. 자물쇠 테스트는 자물쇠만 봐야 한다 |
| **전역 캐시는 테스트를 거짓으로 통과시킨다** | 앞 테스트가 넣어 둔 판단을 뒤 테스트가 캐시에서 받아 **LLM 대역을 한 번도 안 부르고 초록**이 된다. conftest 의 autouse 리셋이 필수다 (재무 캐시가 같은 이유로 이미 있었다) |
| **비인라인 env 는 서버 번들에도 안 남는다** | `ADVICE_API_KEY` 로 카나리 값을 넣고 빌드해 `.next/static` 을 뒤졌더니 없었고 `.next/server` 에도 없었다. `NEXT_PUBLIC_` 이 아니면 빌드 타임 인라인이 아니라 **런타임 조회**라 이미지에 구워지지 않는다 |

### 설계에서 지킨 것

- **규칙 기반 폴백은 캐시하지 않는다.** 폴백은 LLM 이 죽었을 때의 임시 답이라 다시
  만드는 데 돈이 들지 않고, 캐시하면 키가 복구된 뒤에도 TTL 동안 '규칙 기반 판단'
  배지가 계속 뜬다 — **고장이 캐시에 굳는다.** 덕분에 재시도 버튼이 정상 결과에는
  무료(서버 캐시)로, 폴백에는 진짜 재실행으로 동작한다.
- **stage 0 에러를 성공으로 접지 않는다.** 스트림은 정상 종료하면서 에러만 싣고 올 수
  있는데(상류 429 등) 그걸 성공으로 처리하면 **실패가 캐시에 들어가** staleTime 내내
  재생된다.
- **지문은 정렬해서 해시한다.** 같은 기사 묶음이 순서만 바뀌어 오는 일이 있는데 그걸
  '새 기사'로 읽으면 LLM 4회가 이유 없이 나간다. 개수도 함께 넣어 기사가 **사라졌을
  때**도 지문이 바뀌게 한다.
- **캐시 적중이어도 SSE 4단계 계약을 지킨다.** 화면 코드는 캐시였는지 알 필요가 없고,
  사용자에게는 진행 바가 순식간에 끝난 것으로 보인다.
- **`StockAdviceResponse` 통째로 캐시하지 않는다.** 그 안의 `stock_data` 는 504봉이라
  종목 256개면 수십 MB다. 캐시해서 이득인 것은 **다시 만들려면 돈이 드는 것**뿐이다.

### 검증

백엔드 156개(신규 22) / 프런트 64개(신규 7) 통과, `ruff`·`tsc`·`lint`·`build` 통과.

테스트가 **응답이 아니라 LLM 대역 호출 횟수를 직접 센다** — 캐시가 조용히 무력화되는
회귀(키를 심볼 아닌 것으로 바꾸거나 지문에 순서를 섞는 변경)는 응답만 봐서는 안 보인다.

- 같은 종목 2회 요청 → LLM 4회 (8회가 아니라)
- TTL 안에서는 뉴스 조회 대역을 폭발하게 해 둬도 통과 (조회 자체를 안 한다)
- TTL 후 새 기사 → 8회 / 같은 기사 → 4회 유지
- 상한 초과 시 스트리밍 엔드포인트가 `text/event-stream` 이 아닌 **429 + Retry-After**
- 카나리 키로 빌드해 클라이언트 번들 유출 0건 확인

**아직 못 한 것**: 유효한 OpenAI 키가 없어 실제 LLM 왕복으로는 확인하지 못했다.
키가 생기면 같은 종목을 두 번 열어 백엔드 로그에 `AI 판단을 캐시에서 재생합니다` 가
찍히는지 보면 된다.

```python
#          └─ 모든 행에서 거짓. 정렬 항이 통째로 죽는다
```

### ② 자동완성 폴백에서 코스피가 코스닥보다 뒤로 갔다

KOSPI → 이름 길이" 로 적어 두고 정반대로 동작한 셈이다.

## 9회차 — 2026-08-05 · 관심종목 실데이터화 (P2 저장소)

### 범위 — 저장소 먼저, 로그인은 나중

로그인부터 붙이면 프로바이더 선정·세션·계정 화면이 앞에 붙어 저장소에 닿기까지 멀다.
그래서 **소유자를 불투명한 문자열 하나로 추상화**하고 저장소를 먼저 세웠다.

```
지금:   owner_key = "anon:9f3c…"   ← 서버가 발급한 httpOnly 쿠키
로그인: owner_key = "user:42"      ← 세션의 사용자 ID
```

`users.id` 외래키를 걸었다면 사용자 테이블이 생기기 전까지 이 테이블을 **만들 수조차
없었다.** 문자열로 두니 로그인이 붙는 날 할 일이 `transfer_owner()` 한 번(겹치지 않는
행의 `owner_key` UPDATE)으로 끝난다. 그 경로와 테스트를 지금 만들어 뒀다.

**이것은 인증이 아니라 식별이다.** 남의 키를 알면 그 목록을 볼 수 있다 — 그래서 값을
브라우저가 아니라 서버가 만들고(클라이언트가 만들면 아무 값이나 넣어 남의 목록을
조회한다), httpOnly 로 JS 가 읽지 못하게 둔다. 공개 배포 전에 로그인이 필요한 이유다.

### 저장하는 것과 보여주는 것을 나눴다

| 어디서 | 무엇 |
|---|---|
| `watchlist_items` (신규) | 그룹 · 순서 · 보유 · 알림 — **사용자가 정한 것** |
| `listed_companies` | 종목명 · 시장 구분 |
| yfinance `scan_movers` | 현재가 · 등락률 · 3개월 스파크 |

시세를 컬럼에 넣으면 그 순간부터 낡는다. 화면은 항상 최신을 원하므로 조회 시점에
붙인다. 시세는 홈·탐색이 쓰는 `scan_movers` 를 그대로 재사용한다 — 심볼 목록을 주면
한 번의 벌크 다운로드로 이름·시세·스파크를 다 채워 온다.

시세 TTL 캐시의 키는 **심볼 집합**이다. 소유자를 키로 잡으면 종목을 담거나 뺐을 때
낡은 목록을 계속 준다. 집합을 키로 두면 목록이 바뀌는 순간 키가 바뀌어 자동으로
새로 받고, 덤으로 같은 종목을 담은 두 사람이 캐시를 공유한다.

### 이번에 밟은 함정 4개 — 전부 "조용히 틀리는" 종류

| # | 함정 | 어떻게 드러났나 |
|---|---|---|
| 1 | **autogenerate 가 빈 마이그레이션을 냈다** | `db_create_all_on_startup=True` 가 개발 DB에 이미 같은 테이블을 만들어 둬 모델과 DB 사이에 차이가 없었다. 그대로 뒀다면 **로컬은 멀쩡하고 배포에서만** 테이블이 안 생긴다. 손으로 쓰고, 테이블을 지운 뒤 `alembic upgrade head` 로 처음부터 만들어지는지 확인했다 |
| 2 | **쓰기가 매 요청 롤백되고 있었다** | `get_db` 는 커밋하지 않고 세션을 닫는데(`core/database.py`) 새 리포지토리를 `flush()` 로 끝냈다. 화면에는 저장된 것처럼 보이고 새로고침하면 사라진다. `listed_company` 리포지토리는 자기 쓰기마다 커밋하고 있었다 — 규약을 안 따른 쪽이 새 코드였다 |
| 3 | **1종목 시세 조회가 통째로 0건** | `scan_movers._closes_of` 가 `len(symbols)==1` 이면 티커 레벨이 없다고 가정했는데, 지금 핀(yfinance>=1.5)은 1종목에도 MultiIndex 를 유지한다. 모집단 200종목인 홈·탐색은 그 분기를 안 타서 드러난 적이 없었고, **담은 것만 조회하는** 관심종목이 생기며 나타났다. 개수가 아니라 컬럼 모양을 보게 고쳤다 |
| 4 | (검증 중 오인) 한글 `group` 요청이 400 | 서버가 아니라 **Git Bash 가 cp949 로 인자를 뭉갠 것**이었다. 파일 페이로드로 보내니 정상. 셸을 거친 한글 검증은 결과를 믿기 전에 인코딩부터 의심해야 한다 |

### 그중 2번이 남긴 것 — 테스트가 초록인데 운영이 깨졌다

저장소 계약 테스트 18개가 전부 통과하는 동안 운영 경로는 매 요청 롤백하고 있었다.
픽스처가 준 **세션 하나를 계속 쓰기 때문**이다 — 그 안에서는 `flush()` 든 `commit()`
이든 똑같이 보인다.

그래서 `test_watchlist_persistence.py` 를 따로 뒀다. 파일 DB에 **세션을 두 개 열어**
첫 세션이 쓰고 닫은 뒤 두 번째가 다시 읽는다. 커밋을 `flush` 로 되돌리면 이 파일의
3개가 빨개지고 **기존 18개는 여전히 전부 초록이다** — 그 대비가 이 파일의 존재 이유다.

### 화면

- **목록은 더 이상 로컬 state 가 아니다.** 변경 API 가 전부 목록 전체를 돌려주므로
  응답을 그대로 그린다 — 그룹 집계·알림 수·평가손익을 클라이언트가 다시 계산하지 않아
  서버와 어긋날 여지가 없다. 헤더·그룹 탭도 `initial` 이 아니라 최신 목록에서 읽는다.
- **순서만 낙관적**이다. 드래그는 손가락을 떼는 순간 결과가 보여야 한다. 실패하면
  서버가 확인해 준 마지막 목록으로 되돌리고 그 사실을 화면에 띄운다.
- 평가손익 합계는 **금액 가중**이다. 종목별 수익률을 단순 평균하면 100원짜리 1주와
  10만원짜리 100주가 같은 무게가 되어 합계가 실제 손익과 어긋난다.

### Next 16 — `middleware.ts` 가 아니라 `proxy.ts`

소유자 쿠키는 렌더보다 먼저 구워야 한다(서버 컴포넌트는 쿠키를 **읽을 수만** 있다).
그 자리가 Next 16 에서 이름이 바뀌었다 — 예전 이름으로 두면 파일이 조용히 무시되어
쿠키가 영영 안 심기고, **관심종목이 항상 비어 보이는데 오류는 없는** 상태가 된다.
빌드 출력의 `ƒ Proxy (Middleware)` 줄로 등록을 확인했다.

발급한 값은 응답뿐 아니라 **요청 헤더에도** 얹는다. 응답에만 심으면 이번 요청의
렌더는 여전히 쿠키를 못 읽어 첫 화면이 빈 목록이 된다.

### 검증

백엔드 190개(신규 27) / 프런트 64개 통과, `ruff`·`tsc`·`lint`·`build` 통과.
실서버(FastAPI + Next) 왕복으로 확인:

- 평가손익 24.25% — 금액 가중이 맞는 값
- 프런트 첫 방문에 httpOnly 쿠키 발급 → BFF 로 담기 → 화면에 렌더
- **소유자 키가 HTML 에 0건** — 브라우저는 자기 신원 문자열을 보지 못한다

### 범위에서 뺀 것

- **그룹 이동·알림 일괄 설정** — 저장소·API 는 있지만 "어느 그룹으로 옮길지" 고르는

## 10회차 — 2026-08-05 · LLM 프로바이더 OpenAI → Gemini · 5회차 블로커 해소

### 왜 했나

OpenAI 키가 5회차부터 9회차까지 계속 401 이었다. 모델을 `gpt-4o-mini` 로 내려도 같았다 —
**401 은 인증 오류지 모델 오류가 아니다.** 모델 파라미터가 개입하지 않는 `GET /v1/models`
로도 401 이 나는 것을 확인해 키 자체가 거부된다는 것을 못박았다. 그래서 Gemini 키로 옮겼다.

### 바뀐 것은 이 파일 하나다

**`llm.py` 와 설정 몇 줄뿐이고 에이전트·서비스·엔드포인트 코드는 한 줄도 안 건드렸다.**
"LLM SDK 를 import 하는 파일은 하나" 라는 원칙이 세 번째로 값을 했다
(Anthropic → OpenAI → Gemini).

| 개념 | OpenAI (Responses) | Gemini (`generate_content`) |
|---|---|---|
| 시스템 지시 | `instructions=` | `config.system_instruction=` |
| 구조화 출력 | `text_format=Model` | `response_schema=Model` + JSON mime |
| 추론 강도 | `reasoning.effort`(라벨) | `thinking_config.thinking_budget`(**토큰 수**) |
| 거절 | 출력 블록의 `refusal` | `finish_reason` / `prompt_feedback.block_reason` |

가장 다른 곳이 **추론 강도**다. OpenAI 는 `low~max` 라벨을 받지만 Gemini 는 생각에 쓸
토큰 예산을 받는다. `LLM_EFFORT` 를 예산으로 옮기는 표를 `llm.py` 에 뒀다
(low=0 → 생각 끔, max=-1 → 모델이 알아서).

거절 처리도 자리가 다르다. Gemini 는 **입력이 막힌 경우**(`prompt_feedback.block_reason`)와
**출력이 끊긴 경우**(`finish_reason=SAFETY` 등)가 나뉘어 있어 둘 다 봐야 한다. 하나만
보면 상위 계층에 "빈 응답" 으로만 보인다.

### 색인을 다시 만들지 않아도 됐던 이유

프로바이더를 바꾸면 임베딩 차원이 바뀌고, `document_chunks` 는 `vector(1536)` 로 이미
만들어져 있다. 보통은 테이블을 지우고 다시 적재해야 한다.

`gemini-embedding-001` 이 **출력 차원을 지정할 수 있어서**(MRL) 피했다 — 실측으로
1536·768·3072 를 모두 요청해 확인한 뒤 1536 으로 고정했다. 차원을 안 주면 3072 가 와서
테이블과 어긋난다.

### 함께 드러난 것 3개

| # | 무엇 | 왜 지금 드러났나 |
|---|---|---|
| 1 | **RAG 색인이 한 번도 성공한 적 없었다** | `cast(:published_at as date)` 때문에 asyncpg 가 그 파라미터를 date 로 추론하는데 문자열을 넘기고 있었다(`'str' object has no attribute 'toordinal'`). SQL 캐스트는 값이 서버에 닿은 **뒤에** 일어나므로 바인딩을 구해 주지 못한다. 벡터 테이블이 Postgres 전용이라 로컬 SQLite 로는 검증할 수 없었고, 5회차가 "Postgres SQL 경로를 라이브로 못 돌려봤다" 고 적어 둔 바로 그 사각지대다 |
| 2 | **단위 테스트가 실서버를 칠 수 있었다** | `vector_database_dsn` 이 주 DB 로 폴백하면서 개발자 `.env` 의 Supabase 주소가 테스트로 새어 들어왔다. 한 테스트는 **DB 가 닿지 않아서** 통과하고 있었고(연결 실패 → 문서 0건), 주소를 고쳐 DB 가 살아나는 순간 실패로 바뀌었다 — 그때까지 그 테스트는 아무것도 검증하지 않았다. conftest 에서 RAG 를 기본으로 끄고, 쓰는 테스트가 명시적으로 켜게 했다 |
| 3 | **Supabase Direct connection 은 이 PC에서 불가능** | `db.<ref>.supabase.co` 는 **IPv6 전용**인데(A 레코드 없음) 이 PC 는 IPv6 아웃바운드가 안 된다(WinError 10051). URL 을 어떻게 고쳐도 붙지 않는다. 풀러(`aws-0-<region>.pooler.supabase.com`)로 옮겨야 하고, 리전은 탐색으로 찾았다(`ap-northeast-1`) |

## 11회차 — 2026-08-05 · RAG 2단계: 오케스트레이션을 LangGraph 상태 그래프로 (P0)

### 왜 그래프인가 — 선형 코드로 표현할 수 없던 둘

1단계는 `advice_stream.py` 가 순서를 직접 들고 있었다(주가 → 뉴스 → 검색 → 에이전트 →
판단). 읽기는 쉽지만 두 가지를 담을 수 없었다.

1. **검색이 부실하면 질의를 고쳐 다시 찾는다** — `while` 과 카운터를 손으로 관리해야 하고
   그 조건이 함수 중간에 묻힌다.
2. **판단이 없는 근거를 인용하면 다시 만든다** — `for attempt in range(2)` 가 판단 로직과 섞인다.

그래프로 옮기니 그 둘이 **코드가 아니라 구조**가 됐다. `add_conditional_edges` 세 줄이
"언제 되돌아가는가" 의 전부이고, 노드는 자기 일만 한다.

### 전체 모양 (노드 15개)

```
START → collect_price → check_cache ──캐시적중──▶ replay → END
                             │
                        collect_context → check_fingerprint ──기사그대로──▶ replay
                                                  │
                              ┌──────────▶ retrieve
                              │                 │
                              │          grade_documents
                              │           ┌─────┴─────┐
                        rewrite_query ◀───┤ 부족      │ 충분
                          (최대 2회)       └───────────┼──────────┐
                                                       ▼          ▼        ▼
                                                  journalist  economist  analyst   ← 병렬
                                                       └──────────┼──────────┘
                                                                decide            ← fan-in
                                                                  │
                                                               verify
                                                    ┌─────────────┼────────────┐
                                              인용어긋남        정상        2회 실패
                                                    │             │            │
                                              decide 로 복귀  store_result  force_fallback
                                                                  └──────┬─────┘
                                                                        END
```

### LangGraph 를 쓰며 배운 것 넷

| # | 개념 | 이 프로젝트에서의 의미 |
|---|---|---|
| 1 | **리듀서** | 병렬 노드 셋이 같은 키에 쓰면 기본은 **덮어쓰기**라 의견 하나만 남는다. `Annotated[list, operator.add]` 한 줄이 그걸 "이어 붙이기" 로 바꾼다. 오류가 안 나서 조용히 2개를 잃는다 |
| 2 | **조건부 fan-out** | 같은 노드에 조건부 엣지를 두 번 걸 수 없다(`Branch already exists`). 조건 함수가 **노드 이름 리스트**를 돌려주면 그것들이 동시에 시작한다 |
| 3 | **경로 맵** | 조건 함수가 "뜻"(`replay`/`continue`)만 돌려주고 그 뜻이 어느 노드인지는 자리마다 다르게 매핑할 수 있다. 덕분에 캐시 판정 함수 하나를 두 자리에서 재사용했다 |
| 4 | **fan-in 은 공짜** | `asyncio.gather` 를 안 쓴다. 엣지를 세 개 그으면 LangGraph 가 **들어오는 엣지를 전부 기다렸다가** 다음 노드를 실행한다 |

### 실측으로 알게 된 것 — 빈 dict 를 반환한 노드는 `None` 으로 온다

`stream_mode="updates"` 는 `{노드이름: 바뀐것}` 을 준다. 그런데 **아무것도 바꾸지 않은
노드는 빈 dict 가 아니라 `None` 으로 온다.** `store_result` 가 정확히 그런 노드라
(캐시에 넣기만 하고 상태는 안 건드린다) `isinstance(patch, dict)` 가드가 그걸 걸러
**stage 4 가 통째로 사라졌다.** 최소 그래프를 따로 만들어 확인한 동작이다.

### 캐시(7회차)를 그래프 안으로 옮겼다

조건부 엣지 두 개가 됐다: TTL 안이면 뉴스 조회도 건너뛰고(①), TTL 이 지나도 기사가
그대로면 LLM 만 건너뛴다(②). 서비스 함수 안에 숨겨 두면 **"왜 어떤 요청은 1초에
끝나는가" 를 그림에서 못 읽는다.**

`replay` 는 `store_result` 로 가지 않는다. 캐시에서 꺼낸 것을 다시 넣으면 `checked_at`
이 매 조회마다 갱신되어 **기사가 바뀌어도 영원히 안 늙는다.**

### 이번 회차 최대 사고 — 테스트가 실제 Gemini 를 쳤다

`rewrite_query` 노드를 추가했는데 그 노드가 부르는 `ask_text` 를 아무도 대역으로

계속 들어갔다 — 즉 단위 테스트가 돌 때마다 실제 API 를 여러 번 쳤다.

- **설계**: `rag_enabled` 가 false 면 재작성 분기에 아예 안 들어간다. 검색이 꺼져 있는데
  질의를 고치는 것은 LLM 을 쓰면서 아무것도 바꾸지 못하는 일이다

## 12회차 — 2026-08-05 · 로그인 (P2 2단계)

### 기록해 둔 설계를 뒤집었다 — 매직링크 때문

`auth.ts` 주석은 "사용자 테이블이 FastAPI 쪽에 생길 예정이라 어댑터(DB 세션)를 붙이면
저장소가 두 곳으로 갈라진다" 며 JWT 세션을 골라 두었다. 그런데 **매직링크는 검증

셋이었다.

| 안 | 결과 |
|---|---|
| NextAuth 어댑터 | 검증된 구현이 토큰 발급·만료·재사용 방지를 처리. 의존성 2개 |
| FastAPI 가 전부 소유 | 기록된 설계와 일치하지만 **보안 민감 코드를 직접 짜야 한다** |
| 구글만 (매직링크 보류) | 어댑터 불필요, 대신 요구사항 절반 |

어댑터를 골랐다. **인증은 직접 짜지 않는다**가 이 선택의 전부다. 그리고 "저장소가
갈라진다" 는 원래 우려는 **같은 Supabase 를 쓰면서 해소됐다** — 스키마는 alembic 이

### 하나의 DB 를 두 도구가 나눠 쓸 때 — 가장 먼저 밟는 함정

`alembic --autogenerate` 는 **메타데이터에 없는 테이블에 `drop_table` 을 제안한다.**
NextAuth 의 넷(users·accounts·sessions·verification_token)이 정확히 그런 테이블이고,
그대로 실행하면 사용자·세션이 통째로 사라진다.

그래서 `alembic/env.py` 에 `include_object` 필터를 넣었다. 그리고 **탐침을 돌려
확인하다가 같은 위험을 하나 더 찾았다.**

```
op.drop_table('document_chunks')      ← RAG 색인이 통째로 날아갈 뻔했다
op.create_table('document_chunks', …)
```

`document_chunks` 는 `repositories/document_chunk.ensure_schema()` 가 **원시 SQL**로
만든다. pgvector 의 `vector(N)` 과 HNSW·트라이그램 인덱스를 SQLAlchemy 모델로 표현할
수 없어 그렇게 둔 것이고, 그 대가가 이 예외였다. 5회차부터 있던 지뢰인데 주 DB 가
SQLite 라 밟을 일이 없었고, Postgres 로 옮긴 뒤에야 드러났다.

필터를 넣고 다시 탐침하니 **DDL 0건**이다.

### Edge 런타임이 파일을 갈랐다

소유자 해석(`owner.ts`)에 세션 읽기를 넣었더니 빌드가 깨졌다.

```
Middleware: ./node_modules/@auth/core/providers/nodemailer.js
            ./src/auth.ts → ./src/lib/watchlist/owner.ts → ./src/proxy.ts
```

`proxy.ts` 는 **Edge 런타임**이다. 거기서 `owner.ts` 를 쓰는 것만으로 NextAuth 전체가
딸려 들어왔다 — 어댑터의 `pg`(Node 전용 소켓)와 `nodemailer` 까지. 빌드가 통과했어도
Edge 에서는 못 돈다.

쿠키를 **만들고 알아보는 일**(proxy 가 필요한 전부)만 `anon-cookie.ts` 로 떼어 냈다.
세션을 보는 쪽은 `owner.ts` 에 남는다. 파일이 갈라진 이유가 취향이 아니라 런타임이다.

### 소유자 규칙은 함수 하나가 소유한다

```
readOwnerKey()  →  로그인했으면 user:<uuid>, 아니면 anon:<uuid>
```

화면·BFF 어디서도 "로그인했나" 를 다시 판단하지 않는다. **백엔드는 둘을 구분조차
하지 않는다** — `owner_key` 를 외래키가 아니라 불투명한 문자열로 둔 9회차 설계 덕분에
엔드포인트 시그니처가 한 줄도 안 바뀌었다.

승계는 `POST /watchlist/claim` 하나다. 받는 쪽은 **헤더**(`X-Owner-Key`)이고 본문에는
내놓는 쪽만 담는다 — 받는 쪽까지 본문으로 받으면 아무 계정으로나 옮길 수 있다.
승계는 **복사가 아니라 이동**이라, 끝나면 익명 쪽이 비어 있다(테스트가 이걸 고정한다).

익명 키가 httpOnly 쿠키인 것이 여기서 값을 한다: **브라우저 JS 가 못 읽으므로 승계를
서버에서만 할 수 있고**, 클라이언트가 "이 키를 내 계정으로" 라고 말할 수 없다.

### 키가 없어도 화면이 깨지지 않는다

자격 증명이 아직 없으므로 **프로바이더를 환경 변수 유무로 켠다.**

- 키 없음 → 로그인 버튼도 `/login` 폼도 **나타나지 않는다.** 누르면 깨지는 버튼을
  두지 않는다. 대신 `/login` 이 "무엇을 넣어야 켜지는지" 를 안내한다
- 관심종목은 익명 신원으로 그대로 동작하므로 사용자가 잃는 것이 없다
- 키가 `.env.local` 에 들어오면 **코드를 안 고쳐도** 그 수단이 켜진다

### 또 걸린 것 — 테스트가 개발자 `.env` 를 읽고 있었다

`ADVICE_API_KEY` 를 설정하자 무관해 보이는 테스트 3개가 빨개졌다. 그 테스트들이

여부가 그 사람 `.env` 에 달려 있으면 테스트가 아니다.** 10회차의 RAG 누출과 같은 부류라

가입보다 앞선다. 대가는 **사용자를 지워도 그 행이 남는다**는 것이다.

`ON DELETE CASCADE` 가 해 줄 일을 `orphan_service` 가 대신한다. **데이터를 지우는
코드**라 세 겹으로 막았다.

1. **`users` 를 못 읽으면 아무것도 안 한다.** 행이 0개인 것과 테이블이 없는 것은 완전히

   로컬 SQLite 에서 스크립트를 한 번 잘못 돌리는 것으로 충분하다
2. **`user:` 접두사만 본다.** 익명 행은 대응하는 사용자가 원래 없다. 이걸 안 거르면
   로그인 전 사용자의 목록이 통째로 사라진다 — 이 서비스가 저지를 수 있는 최악이다
3. **기본이 모의 실행이다.** 숫자를 먼저 보고 납득한 다음 `--apply` 로 지운다

```bash

uv run python -m scripts.cleanup_orphans --apply    # 실제 삭제
```

계정 삭제 화면이 생기면 그 경로에서 `sweep_orphans` 를 바로 부르면 된다.

이번엔 테스트가 즉시 잡았다는 것이 13회차와 다른 점이다. 그때는 운영에서만 터졌다.

### 한 곳을 고치는 대신 규칙으로 막았다

`nullslast()` 를 빠뜨린 것은 실수이지 설계가 아니다. 그 쿼리 하나를 고쳐 두면 **다음에
정렬을 추가하는 사람이 또 빠뜨린다.** 그래서 개별 쿼리가 아니라 규칙을 검사한다.

`test_postgres_dialect.py` 에 넣었다: 리포지토리 읽기 경로를 한 번씩 태워 **실제로
내보내는 SQL 을 전부 붙잡고**, `ORDER BY <nullable> DESC` 인데 `NULLS` 를 안 적은
자리를 찾는다. nullable 목록은 모델 메타데이터에서 뽑으므로 컬럼이 늘어도 따라온다.

NOT NULL 컬럼은 대상이 아니다 — 거기서는 NULLS 절이 뜻이 없고, 굳이 적으라고 하면
잡음만 늘어 진짜 위반이 묻힌다.

`nullslast()` 를 지우고 돌려 **실제로 빨개지는 것**까지 확인했다. 검사기 자체가
동작하는지도 따로 테스트한다 — 안 잡는 검사기는 없는 것과 같다.

### Postgres 테스트 하네스는 이미 있었다 — 한 번도 안 돌았을 뿐

`TEST_DATABASE_URL` 이 있으면 진짜 Postgres 로, 없으면 SQLite 로 도는 갈래가 이미
`conftest.py` 에 있다(13회차). 세션당 스키마 한 번 + 테스트마다 세이브포인트 롤백이라
설계도 맞다. 다만 **그 값이 아무 `.env` 에도 없어서 그 경로는 실행된 적이 없다.**

안전장치 둘은 실제로 동작하는 것을 확인했다.

```
TEST_DATABASE_URL = DATABASE_URL   → RuntimeError: 같은 DB 를 가리킵니다
TEST_DATABASE_URL = sqlite://…     → RuntimeError: Postgres 여야 합니다
```

전자가 특히 중요하다 — 하네스가 `drop_all` 로 시작하므로 이 검사가 없으면 오타 하나로
실데이터가 통째로 사라진다.

**남은 것은 Supabase 프로젝트를 하나 더 만드는 일뿐이다.** 무료 티어로 충분하고,
`TEST_DATABASE_URL` 에 그 세션 풀러(5432) 주소를 넣으면 그날부터 292개가 운영과 같은
엔진에서 돈다. 그때 이번 다섯 중 셋이 애초에 났을 자리에서 잡힌다.

### SQLite 폴백을 없앴더니 버그가 하나 나왔다

`TEST_DATABASE_URL` 이 비면 인메모리 SQLite 로 도는 갈래를 지웠다. 그 폴백은 13회차의
NULL 정렬 뒤집힘을 낳았고, 이번에 두 번째를 냈다.

폴백을 걷고 실제 Postgres 로 돌리자마자 `test_orphan_service` 하나가 빨개졌다.
`_users_are_readable` 은 `select 1 from users` 가 실패하면 예외를 삼키고 `False` 를
돌려주는데, **Postgres 는 실패한 문장 하나가 트랜잭션 전체를 중단시킨다.** 호출부는
`False` 를 받아 판단할 기회를 얻지만 그 세션으로는 이후 아무것도 못 한다
(`InFailedSQLTransactionError`).

즉 "읽을 수 없으면 `False` 를 주고 호출부가 정한다" 는 그 함수의 계약이 **실제 엔진
위에서는 성립하지 않고 있었다.** SQLite 는 실패한 문장이 트랜잭션을 죽이지 않아 보이지
않았다. 세이브포인트(`begin_nested`) 안에서 물어보도록 고쳤다 — 실패는 세이브포인트까지만
되돌아간다. 테스트도 "거부한 뒤 세션이 계속 살아 있는가" 를 함께 본다.

곁들여 정리한 것:

- `test_watchlist_persistence` 는 파일 SQLite 로 두 세션을 열어 커밋 여부를 봤다.
  `db_session` 은 롤백으로 감싸므로 쓸 수 없어서(그게 검증 대상이다), 실제로 커밋하고
  픽스처가 자기 행을 앞뒤로 지우는 방식으로 바꿨다.
- 설정 자물쇠 테스트를 sqlite 두 종 + mysql 로 파라미터화했다. 막는 대상은 SQLite 가
  아니라 **"Postgres 가 아닌 전부"** 다. 하네스에서 폴백을 걷어내는 것만으로는 부족하다 —
  `.env` 에 `sqlite://` 한 줄이면 되돌아온다.
- `test_postgres_dialect.py` 는 서두에서 "하네스는 인메모리 SQLite 를 쓴다", "SQLite 위에서
  운영 SQL 을 검사할 **유일한** 방법" 이라고 단언하고 있었다. 둘 다 거짓이 됐고, 그대로
  두면 이 파일이 삭제 후보로 읽힌다. 실제 이유로 다시 썼다 — **실행하는 테스트는 그 순간
  테이블에 NULL 이 있어야만 정렬 실수를 잡지만, 컴파일 검사는 데이터와 무관하다.**

지금 실행 경로에 SQLite 는 없다. 남은 `sqlite` 문자열 다섯은 전부 **거부 대상**으로서의
등장이다 — 그것이 SQLite 를 밖에 붙들어 두는 자물쇠다.

### `document_chunks` 만 alembic 밖에 있었다

원시 SQL 로 만들고(`ensure_schema`) alembic 은 `_FOREIGN_TABLES` 로 눈을 감고 있었다.
이유는 "`vector(N)` 과 HNSW·트라이그램 인덱스를 SQLAlchemy 로 표현할 수 없다" 였는데,
확인해 보니 `pgvector.sqlalchemy.Vector` 와 `postgresql_using`/`postgresql_ops` 로
**전부 표현된다.**

밖에 둔 대가가 작지 않았다. 스키마 출처가 둘이라 어느 쪽이 최신인지 알 수 없고, alembic 은
이 테이블에 대해 **아무것도 검증하지 못한다** — 차원이 바뀌거나 인덱스가 사라져도 조용하다.

`models/document_chunk.DocumentChunkRow` 를 단일 출처로 삼았다. `ensure_schema()` 는 그
메타데이터를 `checkfirst` 로 적용하는 얇은 경로가 됐고, `VECTOR_DATABASE_URL` 로 벡터를
다른 인스턴스에 둘 때만 쓰인다.

마이그레이션(`d5e8a1c60f47`)은 **조건부**다. 이 테이블은 마이그레이션보다 먼저 존재했고
운영 DB 에 이미 문서가 있어, 그대로 `create_table` 을 부르면 `DuplicateTable` 로 멈춘다.
있으면 인정하고 넘어가고 없으면 만든다 — 실행 뒤에는 어느 쪽이든 alembic 이 아는 상태가
된다. 확장(`vector`·`pg_trgm`)은 조건 밖에서 항상 보장한다.

차원은 `EMBEDDING_DIMENSIONS` 를 따르게 뒀다. 하드코딩하면 모델을 바꿨을 때 어긋난 사실이
**검색 실패로만** 드러나는데, 설정을 따르면 `alembic check` 가 먼저 diff 로 보여 준다.

확인해 보니 `listed_companies` 2,747건의 `market_cap` 이 **전부 NULL** 이다. 시총 배치가
이 DB 에서 한 번도 성공한 적이 없다(`KRX_ID`/`KRX_PW` 가 비어 pykrx 가 막히고, yfinance
폴백은 검색 요청이 있을 때만 도는데 그 경로가 아직 안 탔다). 그러면 `market_cap desc`
타이브레이크가 통째로 죽어 **물리적 행 순서**가 남는다 — 13회차의 `market == "KOSPI"`,
14회차의 우선순위 정렬과 정확히 같은 종류다. 정렬 항이 죽어도 오류가 안 난다.

신호를 셋으로 겹쳤다. ① 시총(있으면 최선) ② `.KS` 먼저 — **시총이 비었을 때 실제로
일하는 항** ③ 심볼 — 순서를 결정적으로 만든다(없으면 동점 구간이 실행마다 달라져
"왜 이 종목이 먼저인가" 를 설명할 수 없다).

고치고 다시 돌리니 **30종목 중 28종목**에서 날짜를 얻었다. 1/12 → 28/30 이다.

> `market_cap` 이 비어 있다는 사실 자체는 이 회차의 산출물이 아니다. 자동완성 랭킹과
> 등락률 모집단(`top_by_market_cap`)도 같은 값을 쓰므로 그 둘도 지금 폴백 정렬로
> 돌고 있다. 시총 배치를 한 번 돌리는 것이 남은 일이다.

### 날짜 읽는 규칙을 두 벌로 두지 않았다

`exDividendDate` / `earningsTimestampStart` 를 읽는 규칙에는 실측으로만 알 수 있는
함정이 셋 있다 (`earningsTimestamp` 는 **직전** 발표일이다 · 배당락은 UTC 인데 실적은
KST 다 · `ticker.calendar` 폴백은 하루가 밀린다). 원래 `fundamentals.py` 안에만 있었고
배치가 같은 날짜를 읽어야 했다.

복사하지 않고 `yfinance/calendar.py` 로 옮겨 단일 출처로 삼았다. `fundamentals.py` 가
그것을 부른다. 배치가 `fetch_stock_fundamentals` 를 그대로 쓰지 않는 이유는 비용이다 —
그 함수는 `ticker.info` 외에 밸류에이션·손익계산서까지 부르므로 일정만 필요한 배치에서
종목당 3배를 낸다.

### 화면이 "없음" 과 "아직" 을 구분한다

배치가 하루 200종목씩 채우므로 초기에는 **일정이 없는 것**과 **아직 안 물어본 것**이
똑같이 빈 목록으로 도착한다. 뭉뚱그려 "이번 주 예정된 일정이 없습니다" 라고 쓰면 그건
거짓말이다. 그래서 응답에 `covered`/`universe_size` 를 함께 내고 화면이 그 둘을 나눠
말한다 — 지금 실제로 29/2,703 이라 "1% 수집됨, 남은 종목에 일정이 있을 수 있습니다"
가 뜬다.

같은 이유로 **일정에는 목 데이터를 두지 않았다.** 등락률은 눈대중으로 보는 값이지만
날짜는 사람이 그걸 보고 일정을 잡는다. `USE_MOCK` 에서도 `calendar: null` 이다.

한 줄은 종목이 아니라 **일정 하나**다. 같은 종목에 실적발표와 배당락이 모두 있으면 두
줄이 나온다 — 한 줄로 합치면 이 목록의 축(날짜)으로 정렬할 수 없다.

### 따라잡기 배치를 돌렸고, 그러다 내가 만든 결함으로 데이터를 지웠다

시총·일정 두 배치를 상한만 올려 연달아 돌렸다. 결과가 갈렸다.

**시총은 성공.** KRX 벌크는 로그인 벽에 막혔고(예상대로) yfinance 폴백이 140초에
865종목을 채웠다. 처음으로 실제 시총이 들어왔다 — 삼성전자 1,516조 · SK하이닉스
1,009조 · SK스퀘어 · 현대차 · 삼성전기 순이다. 그 즉시 일정 배치의 우선순위가 제대로
동작하기 시작했다(직전까지 무명 코스닥부터 채우던 자리에 시총 상위가 올라왔다).

**일정은 데이터를 지웠다.** 2,703종목이 **113초** 만에 0건으로 끝났다 — 실제 왕복이면
5분 이상이다. 시총 배치가 방금 `get_info()` 를 2,747번 쳤기 때문에 야후가 전부
거부한 것이다. 문제는 그 0건이 조용히 넘어가지 않고 **이미 수집돼 있던 29종목의 날짜를
NULL 로 덮었다**는 것이다. `calendar_updated_at` 까지 찍혀서 방금 확인한 행처럼 보였다.

원인은 내가 그렇게 만들었다. `_fetch_one` 이 **실패와 "일정 없음" 을 같은 빈 값으로
뭉갰고**(그게 의도라고 주석까지 적었다), 저장 계층은 그 빈 값을 곧이곧대로 덮어썼다.
덮어쓰기 자체는 옳다 — 발표가 끝나면 다음 분기 날짜로 바뀌어야 한다. 틀린 것은
**아무것도 모르는 상태를 "없음" 이라고 단정한 것**이다.

두 겹으로 고쳤다.

1. `_fetch_one` 이 `None`(응답 못 받음)과 `CalendarDates()`(응답했고 일정 없음)를
   구분한다. 빈 `info` 도 실패로 본다 — 살아 있는 종목은 항상 채워진 dict 를 준다.
   응답 못 받은 종목은 `answered` 에서 빠져 **아무것도 기록되지 않고** 다시 물어본다.
2. 응답률이 절반 밑이면 배치를 통째로 버린다. 1번만으로도 전멸은 막히지만, 공급자가
   조이기 시작해 **소수만 통과하는 중간 상태**에서는 그 소수의 "일정 없음" 이 멀쩡한
   날짜를 지운다. 표본이 무너진 배치는 부분 반영도 하지 않는 편이 안전하다.

가드를 수확률(날짜 얻은 비율)로 걸지 않은 것이 중요하다. 소형주 배치는 일정이 잡힌
종목이 원래 드물어 0건이 정상인 날이 있고, 그때 버리면 그 종목들이 타임스탬프를 못
받아 큐 맨 앞에 영영 남는다. 수확 0건은 **버릴 근거가 아니라 볼 근거**라 로그로만 남긴다.

### 테스트를 쓰고 나서 그 테스트가 가짜인 것을 발견했다

고친 뒤 "되돌리면 빨개지는가" 를 확인했더니 응답률 가드 테스트가 **가드를 빼도
통과했다.** `answered=[]` 로 썼는데 빈 목록은 리포지토리가 먼저 걸러내(`if not
answered`) 가드까지 도달하지도 않았다 — 검사 대상을 안 지나가는 검사기였다.

3종목 중 1종목만 응답하고 그 하나가 비어 있는 경우로 바꾸니 제대로 빨개졌다.
반대 방향(정상 응답률 + 날짜 0건은 반영해야 한다)도 함께 고정했다.

13회차부터 반복된 교훈이 또 나왔다 — **회귀 테스트는 통과하는 것보다 틀렸을 때
실패하는 것이 본체다.**

### 남은 것

> **17회차에서 셋 다 처리됐다.** 야후는 3일 만에 풀렸고, "두 배치를 연달아 돌리지
> 않는다" 는 규칙은 **배치를 하나로 합쳐 없앴다.** 아래는 당시 기록 그대로 남긴다.

- **야후가 아직 우리를 막고 있다.** 40종목 요청에 0종목 응답이다. 회복까지 시간이
  필요하고, 그때 일정 배치가 다시 돌면 값이 채워진다. 지금 `covered` 는 0/2,703 이다.
- **두 배치를 연달아 돌리지 않는다.** 둘 다 종목당 `get_info()` 를 부른다. 평소의
  하루 1회 상한(400 / 200)으로는 겪지 않고, 따라잡기처럼 상한을 올릴 때만 나온다.
  `calendar_service` 모듈 주석에 적어 뒀다.
- 시총은 865/2,747 이다. 나머지는 실패했거나(상장폐지·해외 계열) 값이 없는 종목이고,
  대형주가 우선 채워져 랭킹 목적으로는 충분하다. 다음 배치가 다시 시도한다.

## 17회차 — 2026-08-10 · 스크리너(조건 검색) — P2 · 배치 둘을 하나로

### 시작은 "야후가 풀렸나" 였다

16회차가 끝날 때 야후는 우리를 막고 있었다. 3일 뒤 8종목으로 찔러 봤다.

```
005930.KS SamsungElec   000660.KS SK hynix   373220.KS LG Energy Solution ...
8/8 응답 · 2.1초
```

**풀렸다.** 같은 자리에서 pykrx 도 확인했는데 이쪽은 여전히 막혀 있다 —
`get_market_cap_by_ticker` 도 `get_market_fundamental` 도 "KRX 로그인 실패:
KRX_ID 또는 KRX_PW 환경 변수를 찾지 못했습니다" 로 떨어진다. 즉 **전 종목 벌크는
지금 존재하지 않는 선택지이고, 지표의 유일한 소스가 yfinance 다.** 이 사실 하나가
아래 설계를 거의 다 결정했다.

### 지표 배치를 새로 만들지 **않았다** — 있던 배치를 넓혔다

스크리너에는 PER·PBR·ROE·배당수익률이 필요하다. 자연스러운 다음 수는 "지표 배치를
하나 더 만든다" 인데, 그러면 종목당 `get_info()` 를 부르는 배치가 **셋**이 된다.
16회차에 둘이었을 때 이미 야후가 전 종목 요청을 거부했었다.

그때 대응은 주석이었다 — "두 배치를 연달아 돌리지 않는다". 이번에는 그 규칙을
지키는 대신 **지킬 필요가 없게** 만들었다.

| | 16회차 | 17회차 |
|---|---|---|
| 일정 배치 | `get_info()` × N | — |
| 시총 배치(yfinance 폴백) | `get_info()` × M | 사실상 정지 |
| 스냅샷 배치 | — | `get_info()` × N (+ 밸류에이션 × N) |

일정 두 날짜와 지표 넷은 **같은 응답**에서 나온다. PER/PBR 만 `get_valuation_measures()`
가 하나 더 붙는데, 실측 0.18초로 info(0.5초)의 1/3 이라 종목당 비용이 2배가 아니라
1.4배다. 시총도 그 info 에 들어 있으므로 함께 채운다 — 그러면 시총 배치의 yfinance
폴백은 `market_cap IS NULL` 인 종목만 물어보므로 **스스로 조용해진다.** 지우지 않고
그대로 둔 이유는 그쪽이 KRX 벌크의 폴백이기도 하고, 그 코드가 13·14회차에 잡은
정렬 버그의 회귀 테스트를 달고 있기 때문이다.

파일도 그에 맞춰 갈랐다. **쓰는 쪽 하나, 읽는 쪽 둘**이다.

```
snapshot_service   배치 (쓴다)
   ├─ calendar_service   오늘의 일정 (읽는다)
   └─ screener_service   조건 검색  (읽는다)
```

`yfinance/calendar.py` 에는 날짜 해석 규칙만 남기고 수집을 `yfinance/snapshot.py` 로
옮겼다. 규칙의 단일 출처라는 그 파일의 역할은 그대로다 — 상세 화면과 배치가 둘 다
`extract_calendar_dates` 를 부른다.

### 16회차 사고가 **한 겹 더 깊은 형태로** 다시 나타났다

16회차의 교훈은 "응답을 못 받은 것을 '없음' 으로 단정하지 마라" 였고, 그 구분은
종목 단위였다(`answered` 에 들어갔는가). 지표에는 그것으로 표현되지 않는 경우가 있다.

```
info 성공 + 밸류에이션 실패  →  종목은 "응답함"인데 PER 만 모른다
```

`get_valuation_measures()` 는 **별개의 호출**이라 따로 실패한다. 이걸 뭉개면 호출 한
번 실패했을 때 이미 적재된 PER 이 NULL 로 덮인다 — 16회차와 정확히 같은 사고가
컬럼 단위로 일어난다. 그래서 값과 함께 `valuation_ok` 를 실어 보내고, 저장 계층이
세 갈래로 나눠 쓴다.

| 값 | 규칙 | 근거 |
|---|---|---|
| ROE · 배당수익률 | 그대로 덮어쓴다 | info 응답을 받았으니 없으면 없는 것이 사실이다 (배당 중단은 반영돼야 한다) |
| PER · PBR | `valuation_ok` 일 때만 | 그 호출만 실패할 수 있다 |
| 시가총액 | **있을 때만** | 이 컬럼은 writer 가 둘이다. KRX 경로가 "있는 값만" 이라, 이쪽만 NULL 을 반영하면 배치 순서에 따라 값이 나타났다 사라진다 |

`fundamentals_updated_at` 을 `calendar_updated_at` 과 따로 둔 것도 같은 이유다.
하나로 합치면 밸류에이션만 실패한 날 화면이 **옛 PER 을 오늘 값이라고** 말한다.

### 인덱스를 안 걸었다 — 바로 앞 마이그레이션과 반대 판단이다

f2c9b47ad831(일정)은 컬럼 셋에 전부 인덱스를 걸었는데 a4d72f9e51c3(지표)은 하나도
안 걸었다. 일관성이 없어 보이므로 근거를 남긴다.

- 일정 컬럼은 용도가 "오늘부터 N일" 범위 조회 **하나로 고정**이고,
  `calendar_updated_at` 은 배치 큐의 정렬 키라 매 배치마다 쓰인다.
- 지표는 조건 조합이 매번 다르다(PER 만 · PER+PBR · 배당만). 단일 컬럼 인덱스로
  덮이지 않는다. 게다가 이 표는 2,747행이라 seq scan 이 이미 한 페이지 수준인데,
  배치가 하루 한 번 전 행을 갱신하므로 인덱스는 **쓰이지 않으면서 쓰기 비용만** 낸다.

행 수가 수십만이 되면 그때 실제 조건 분포를 보고 복합 인덱스를 건다.

### 화면: 필터를 얹지 않고 **탭으로 갈랐다**

원래 계획은 "`/stocks` 에 필터를 얹는 형태" 였다. 만들면서 뒤집었다 — 두 목록은
**데이터 경로가 아예 다르다.**

|---|---|---|
| 출처 | 등락률 스냅샷(메모리) | DB |
| 모집단 | 시가총액 상위 200종목 | 상장 전 종목 2,703 |
| 갱신 | 5분 | 하루 1회 배치 |
| 가진 것 | 가격·등락률·스파크라인 | 지표 다섯 |

같은 표에 조건 칩만 늘렸다면 사용자는 'PER 10 이하' 로 나온 목록이 전 종목에서
걸러진 것이라 믿었을 텐데, 실제로는 **200종목 안에서만** 걸러졌을 것이다. 오류 없이
틀리는 종류다. 합치려면 전 종목 시세를 매번 스캔하거나(수 분) 조건 검색을 200종목으로
줄여야 하는데 어느 쪽도 답이 아니라서, 탭이 그 경계를 눈에 보이게 만든다.

같은 이유로 조건 검색 표에는 **가격 열이 없다.** 넣으면 대부분의 행이 빈칸이 된다.

### 적자 기업이 '가장 싼 종목'으로 맨 앞에 온다

PER 은 순손실이면 음수다. 'PER 10배 이하' 를 상한만으로 만들면 이렇게 된다.

```
1  적자테크   PER -3.20   ← 숫자상 가장 낮다
```

숫자는 맞고 투자 판단으로는 완전히 틀린, 스크리너의 고전적인 함정이다. 프리셋이
하한을 항상 함께 걸고(`per_min: 0`), 하한을 지우면 빨개지는 테스트를 붙여 뒀다.
그 테스트는 **하한이 없을 때 적자가 앞에 온다는 것까지** 확인한다 — 전제가 바뀌면
테스트가 먼저 알려준다.

### URL 에 숫자가 아니라 프리셋 이름을 싣는다

`?per=low` 이지 `?per_min=0&per_max=10` 이 아니다.

1. 주소가 읽힌다. 공유된 링크를 보고 무슨 목록인지 안다.
2. 임의의 숫자가 들어올 자리가 없다 — 열거에 없으면 기본값으로 떨어진다.
3. **경계값을 한 곳이 소유한다.** 'PER 10배 이하' 가 실제로 어떤 범위인지는
   `model/screener.ts` 의 표 하나에만 있고 화면·링크·API 호출이 그것을 읽는다.

자유 입력은 일부러 넣지 않았다. 그러려면 클라이언트 상태와 폼이 필요해 이 화면
전체가 브라우저로 내려간다. 지금 조건 칩·탭·표는 **전부 서버에서 HTML 로 끝나고**,
브라우저로 가는 것은 검색 트리거뿐이다.

### 실측으로 알게 된 것 — 야후의 실질 상한은 1회 ~500종목이다

따라잡기를 250종목씩 청크로 돌리며 응답률을 봤다.

```
[1] 250종목 → 250 응답(100%) · 30초   일정 190 · 지표 246 반영
[2] 250종목 → 250 응답(100%) · 28초   일정 147 · 지표 250 반영
[3] 250종목 → 112 응답(45%)  · 18초   ← 쓰지 않고 중단
```

3번째에서 `Too Many Requests` 와 `Invalid Crumb`(401)이 섞여 나왔다. 즉 **종목 500개
(호출 1,000회) 언저리가 한 번에 낼 수 있는 최대**다. 하루 1회 상한이 200이므로
평상시에는 절대 닿지 않고, 이번처럼 따라잡기를 할 때만 만난다.

중요한 것은 3번째 청크가 **아무것도 쓰지 않고 끝났다**는 것이다. 16회차였다면 바로
이 상황이 데이터를 지웠다.

### 로그인을 켜고 나서야 보인 것 — **담기 버튼이 아예 없었다**

키를 꽂고 화면을 돌아보니 로그인·로그아웃·담기 버튼이 안 보인다는 제보가 왔다.
셋을 확인해 보니 원인이 서로 달랐고, 하나는 "안 보이는" 것이 아니라 **없는** 것이었다.

| 버튼 | 실제 상태 |
|---|---|
| 관심 종목에 담기 | **존재하지 않았다.** `useWatchlistMutations.add` 를 부르는 곳이 0곳 |
| 로그인 · 로그아웃 | `AccountMenu` 는 있는데 **`/watchlist` 한 화면에만** 붙어 있었다 |
| 둘 다 | 붙어 있어도 `hidden md:flex` 라 768px 미만에서는 사라졌다 |

첫 줄이 이 프로젝트가 계속 마주치는 그 종류다. `add` 는 12회차부터 훅에 있었고
BFF 라우트(`POST /api/watchlist`)도 백엔드도 멀쩡했다. 다만 **누르는 자리가 없었다.**
관심종목 화면은 이미 담긴 것을 정렬·삭제·그룹핑하는 화면이라, 목록은 구조적으로
영원히 비어 있었다 — 그런데 화면에는 "아직 안 담았네" 로만 보인다. 오류도 로그도
없다. 9·12회차에 저장·승계·소유자 규칙을 그렇게 공들여 만들고도 정작 **첫 한 건이
들어갈 문**이 없었던 셈이다.

담는 자리는 목록이 아니라 **종목을 보고 있는 화면**이다. 담을지 정하는 순간이 거기다.
그래서 `WatchToggle` 을 종목 상세의 제호 우측에 둔다(2a·2b 양쪽). 상세 페이지는 이미
관심목록을 받아 오므로 담김 여부를 추측하지 않고 그 목록에서 읽는다 — 콘솔 뷰는
좌측 레일이 같은 목록을 그리고 있어서, 두 경로로 받으면 한 화면 안에서 어긋난다.

`AccountMenu` 는 모든 화면의 제호로 올렸다. 로그인·로그아웃이 화면마다 다른 자리에
있으면 안 되고, 특히 "관심종목 화면에서만 로그인할 수 있다" 는 순서가 거꾸로다 —
로그인은 관심종목을 **쓰기 전에** 하는 일이다.

모바일은 숨기는 대신 **글자를 접었다.** 하단 탭바에 계정 자리가 없어서, 감추면
좁은 화면에서는 로그인할 방법도 로그아웃할 방법도 완전히 사라진다. 글리프는 남으므로
44px 히트 영역과 `aria-label` 이 그대로 산다. 아이콘은 쓰던 세트를 그대로 늘렸다
(`shared/ui/Icon.tsx` 레지스트리에 boxicons `login`·`logout` 추가).

### 구글 로그인을 **취소**하면 "서버 설정 오류" 가 떴다

취소 버튼을 누르면 `/api/auth/error?error=Configuration` 으로 튕기고 검은 화면에
"Server error — There is a problem with the server configuration." 만 남았다.
제호도 없고 돌아갈 링크도 없어서 사이트를 벗어난 것처럼 보인다.

원인이 어이없다. 구글의 discovery 문서가 이걸 광고한다.

```
"authorization_response_iss_parameter_supported": true
```

그래서 Auth.js(oauth4webapi)는 콜백 응답에 `iss` 가 **있어야** 한다고 검증하는데,
구글은 **성공 응답에만** `iss` 를 싣는다. 취소는 `error=access_denied` 만 담아
돌아오므로 `iss` 검증에서 **먼저** 터지고, "사용자가 취소했다" 라는 정보는 그
예외에 묻힌다. Auth.js 는 그것을 `CallbackRouteError` 로 감싸고, 에러 페이지는
공개 코드 넷(`Configuration`·`AccessDenied`·`Verification`·`Default`) 중
`Configuration` 으로 내보낸다 — **취소가 설정 오류로 도착한다.**

두 가지를 했다.

- `pages.error` 를 `/login` 으로 돌린다. 실패를 우리 화면에서 받으면 그 자리에서
  다시 시도할 수 있다.
- `?error=` 를 사람이 읽는 문장으로 옮기되, **`Configuration` 을 "설정이
  잘못됐습니다" 로 번역하지 않는다.** 이 코드로 도착하는 가장 흔한 경로가 취소이기
  때문이다. "취소했다면 다시 시도하면 되고, 반복되면 로그에 원인이 남는다" 로
  양쪽을 다 담았다 — 어느 쪽인지 화면이 단정하지 않는 편이 정직하다.

색은 새로 만들지 않았다. 이 팔레트에서 빨강·파랑은 등락 방향이 소유하고
(`lib/format/direction`) 앰버는 AI 액션이다. 셋 중 하나를 빌리면 화면 전체의 색
규약이 흐려져서, 실선 테두리와 글리프로만 구분한다.

**로그인 자체는 이 문제와 무관하다** — 성공 응답에는 `iss` 가 들어 있다.

## 18회차 — 2026-08-10 · 관리자 화면 (회원 관리 · 운영 현황)

### 화면보다 **인가**가 문제였다

관리자 화면을 만들자는 요청에서 먼저 확인한 것은 UI 가 아니라 권한 구조다. 없었다.

| 확인한 것 | 사실 |
|---|---|
| `users` 테이블 | `id · name · email · emailVerified · image` — **role 컬럼 없음** |
| Next 인가 | `authorized: () => true` — 모든 경로가 공개 |
| 백엔드 인증 | **없음.** `X-Owner-Key` 는 코드가 스스로 "인증이 아니라 식별" 이라고 못박음 |
| 백엔드 자물쇠 | `ADVICE_API_KEY` 하나, AI 판단 2개만 |

여기서 진짜 난제가 나온다. 관리자 API 를 FastAPI 에 만들면 **백엔드는 프런트가 보내는
"나 admin이야" 를 검증할 수단이 없다.** 세션은 프런트에 있고 `X-Owner-Key` 는 위조
가능한 식별자다. 그대로 두면 권한 상승이 헤더 한 줄이 된다.

### 두 겹으로 나눴다 — 그리고 **어느 쪽도 다른 쪽을 대신하지 못한다**

```
브라우저 ──(세션 쿠키)──▶ Next /admin/*        ← 여기가 인가다 (role 검증)
                            │
                            └──(X-Admin-Key)──▶ FastAPI /admin/*   ← 2차 방어선
```

- **Next 가 인가를 소유한다.** `requireAdmin()` 이 세션과 `users.role` 을 보고,
  아니면 404 다(403 이 아니라 404 인 이유는 아래).
- **`X-Admin-Key` 는 인증이 아니다.** 그 키만 아는 사람은 로그인 없이도 백엔드를
  부를 수 있으므로, 백엔드는 "이 요청이 관리자에게서 왔다" 를 주장할 수 없다.
  행위자(`X-Admin-Actor`)도 감사 로그용이지 권한의 근거가 아니다.

**AI 판단 키를 재사용하지 않았다.** 잃었을 때의 크기가 다르다 — AI 키가 새면 남이
우리 토큰을 태우고, 관리자 키가 새면 남이 자기 계정에 관리자 권한을 준다. 하나로
두면 **매 AI 요청에 실려 나가는 값이 가장 강한 권한을 갖게** 된다.

미설정일 때의 동작도 반대로 뒀다. advice 는 키가 없으면 통과시키는데(로컬 개발이
키 없이 돌아야 하고 잃는 것이 토큰뿐이다), 관리자는 **닫는다.** 설정을 빠뜨린 서버가
권한 부여 API 를 공개하는 것보다 화면이 안 열리는 편이 비교할 수 없이 낫다.

### 첫 관리자 — `ADMIN_EMAILS` 는 편의가 아니라 **복구 경로**다

권한은 `users.role` 이 들지만, 그것만 두면 자기 권한을 잘못 지웠을 때 복구 수단이
DB 직접 수정뿐이 된다. 그래서 환경 변수에 적힌 이메일은 DB 와 무관하게 항상 관리자다.

이 규칙을 **프런트에만** 둔 것도 의도다. 백엔드는 세션을 못 보므로 이메일을 알 수
없고, 안다 해도 헤더로 받은 값이라 믿을 수 없다.

### 잠기지 않기 위한 규칙 넷

되돌릴 수 없는 일이라 화면이 아니라 서비스 계층에 뒀다 — 버튼을 감추는 것은 보안이
아니고, API 는 화면 없이도 불린다.

1. **마지막 관리자는 강등되지 않는다** — 아무도 못 들어오는 상태를 만들 수 없다
2. **자기 자신은 강등하지 않는다** — 되돌리려면 방금 잃은 권한이 필요하다
3. **삭제로도 우회할 수 없다** — 강등만 막으면 "지우면 되지" 가 남는다
4. **거절도 기록한다** — 누가 마지막 관리자를 계속 두드리는지는 봐야 할 신호다

### 감사 로그에 외래키를 걸지 않았다

`actor_user_id`·`target_user_id` 는 그냥 문자열이다. **계정 삭제가 이 로그가 기록하는
행위 중 하나**라, 외래키가 있으면 그 기록이 대상과 함께 사라지거나(CASCADE) 삭제
자체가 막힌다(RESTRICT). 관심종목이 `owner_key` 를 문자열로 드는 것과 같은 선택이고
같은 대가다 — 정합성을 DB 가 아니라 우리가 진다.

같은 이유로 `target_email` 을 **복사**해 둔다. id 만 남기면 지워진 계정의 로그가
"누구인지 알 수 없는 uuid" 가 되어 읽을 수 없다.

그리고 권한 변경과 기록은 **한 트랜잭션**이다. 나눠 커밋하면 그 사이에 프로세스가
죽었을 때 "권한은 바뀌었는데 기록이 없는" 행이 남는다.

### 회원 삭제가 `cleanup_orphans` 가 비워 둔 자리를 채웠다

관심종목·투자 성향은 소유자를 외래키가 아니라 문자열로 든다. `users` 행만 지우면
그 사람의 데이터가 남고, 그건 스크립트가 나중에 치워야 할 빚이다. 그 스크립트 주석이
정확히 이 자리를 예고해 두었다.

> "계정 삭제 화면이 생기면 그 경로에서 `sweep_orphans` 를 바로 부르면 된다"

실제로는 `sweep_orphans`(전체 훑기)가 아니라 **그 사람의 행만** 같은 트랜잭션에서
지운다. 삭제 한 번에 전 테이블을 훑을 이유가 없다. 전체 훑기는 여전히 스크립트의
몫으로 남는다 — DB 를 직접 만진 경우를 대비한 그물이다.

### 403 이 아니라 404 로 끊는다

403 은 "여기 뭔가 있는데 네 권한이 부족하다" 를 알려 준다. 로그인 화면으로 보내는
것도 마찬가지로 "이 경로는 실재한다" 는 신호다. 관리자 화면은 존재 자체를 광고할
이유가 없어서, **없는 것처럼** 보이게 했다.

### 실측으로 알게 된 것 — `notFound()` 는 상태 코드를 못 바꾼다

프로덕션 빌드로 익명 접근을 확인했더니 이랬다.

```
/admin  →  200   (내용은 not-found, 관리자 내용 0건)
```

원인은 루트 `loading.tsx` 가 만든 Suspense 경계다. 셸이 먼저 흘러 나가면서 헤더가
이미 나갔기 때문에, 그 뒤에 `notFound()` 가 불려도 상태를 되돌릴 수 없다. **내용은
막혔지만 상태 코드는 거짓말을 하고 있었다.**

그래서 `proxy.ts` 에 한 겹을 더 뒀다. Edge 라 DB 를 못 보므로 판정할 수 있는 것은
"세션 쿠키가 아예 없다 = 로그인한 적이 없다" 하나뿐인데, 그것만으로 충분한 이유가
둘이다: 익명 요청은 대부분 스캐너이고 그쪽에 진짜 404 를 줄 수 있으며, 로그인도 안
한 요청에 세션 조회와 렌더를 태우지 않는다.

**이 검사를 인가로 착각하면 안 된다.** 쿠키만 있으면 통과한다 — 그 뒤를 페이지의
`requireAdmin()` 이 받는다. 검증도 그렇게 나눠서 했다.

```
익명 (쿠키 없음)      → 404  (proxy 가 끊는다)
위조 쿠키            → 200 이지만 관리자 내용 0건 (페이지 가드가 끊는다)
/stocks              → 200  (영향 없음)
```

또 하나: 그 과정에서 `/admin` 이 **"시장 현황을 불러오는 중입니다"** 를 띄우고
있었다 — 루트 스켈레톤이 잡힌 것이다. `app/admin/loading.tsx` 를 따로 뒀다.

### 버튼을 줄에 추가했더니 옆 버튼이 커 보였다

담기·로그인을 제호 우측에 올린 뒤 "AI 판단 버튼이 비정상적으로 크다" 는 말이 나왔다.
재 보니 실제로 혼자 달랐다.

| 컨트롤 | 가로 | 세로 | 글자 |
|---|---|---|---|
| 담기 · 로그인 | 12px | 8px | 13 |
| 뷰 토글 · 테마 토글 | 10px | 8px | 9.5 |
| **AI 판단 열기** | **18px** | **9px** | 13 + 솔리드 + 점 |

**버튼은 그대로였고 이웃이 생긴 것이다.** 컨트롤이 둘뿐이던 시절에는 그 여유가
"주 액션" 으로 읽혔는데, 컴팩트한 버튼 다섯이 같은 줄에 서자 정렬이 무너져 보였다.
크기로 위계를 만든 것이 문제였다 — 주변이 전부 테두리 버튼이면 **솔리드 하나로
이미 위계가 선다.** 크기는 줄에 맞추고 강조는 채움에 맡겼다.

같은 줄 문제로 종목 탐색·조건 검색의 마스트헤드 검색 필드도 뺐다. 250px 필드가
컴팩트한 버튼들 사이에서 혼자 넓었다. 잃는 것은 거의 없다 — ⌘K 는 어디서나 열리고,
모바일은 하단 탭바에 검색이 그대로 있으며, **홈이 이미 마스트헤드 검색을 비워 두고
있어**(FindBand 가 본문 첫 블록을 통째로 쓴다) 오히려 그쪽과 맞는다.

두 탭을 **함께** 비운 것이 요점이다. 한 화면의 두 탭이 제호 구성이 다르면 탭을
옮길 때마다 줄이 흔들린다.

### 크기를 맞췄더니 이번엔 좁은 폭에서 무너졌다

폭을 줄여 보니 이렇게 됐다.

```
[검색 필드][TERMINAL][☆ 담기][CONSOLE][AI  ][⇥ 로그인]
                                       판
                                       단
                                       열
                                       기
```

원인이 둘이었다.

1. 제호 제목이 `whitespace-nowrap` 이라 안 줄어드는데 **우측 덩어리만 `min-w-0`**
   이라 압박을 전부 받았다.
2. 그 안의 버튼에 `flex-none` 이 없어 내용보다 작게 눌렸고, `whitespace-nowrap`
   도 없어 눌린 폭에 맞춰 글자가 세로로 쌓였다.

고친 방식이 요점이다. **폭을 계산해 맞추지 않았다.** 버튼마다 `flex-none`·
`whitespace-nowrap` 을 달아 눌리지 않게 하고, 그래도 안 들어가면 덩어리가 다음
줄로 넘어가게 했다(`flex-wrap`). 계산해 맞추는 방식은 컨트롤을 하나 더할 때마다
다시 깨지는데, **실제로 담기·계정을 더하면서 그렇게 깨졌다.** 같은 실수를 두 번
하지 않으려면 안전망이 있어야 한다.

### 그래도 안 됐다 — 줄이는 대신 **성격으로 갈랐다**

안전망이 붙자 무너지지는 않았는데, 폭을 더 줄이니 이렇게 됐다.

```
                         [TERMINAL] [☆ 담기] [CONSOLE] [● AI]
종목 원장. The Stock Ledger                        [⇥ 로그인]
2026. 08. 10 월요일 · 장 마감 …
```

로그인 혼자 둘째 줄로 내려가 헤더가 계단이 됐다. `flex-wrap` 은 **무너짐을 막는
장치이지 좋은 배치가 아니다.**

여기서 폭을 더 짜내는 대신 다시 물었다 — **이 줄에 왜 여섯이 있나.** 보니 성격이
다른 둘이 섞여 있었다.

| | 뜻 |
|---|---|
| 검색 · 테마 · 계정 | **어느 화면에나** 있는 전역 컨트롤 |
| 담기 · AI 판단 · 뷰 전환 | **지금 보는 종목에만** 뜻이 있는 액션 |

후자를 헤드라인 아래 액션 줄로 내렸다. 그러자 세 가지가 한꺼번에 풀렸다.

- 제호가 **다른 화면과 같은 구성**이 된다(검색·테마·계정). 두 회차 앞에서 "화면이
  고르게 통일된 느낌" 을 물었던 그 방향이다.
- 액션이 **대상 옆**에 온다. 담을지 정하는 순간은 종목명과 시세를 본 직후다.
- 컨트롤을 더 추가해도 두 줄이 각자 여유를 갖는다. 폭 계산으로 맞춰 뒀다면
  다음 버튼에서 또 깨졌을 것이다.

액션 줄을 오른쪽 정렬로 둔 것은 제호의 컨트롤과 **같은 세로선**에 놓기 위해서다 —
액션을 찾는 눈이 한 열에 머문다. 모바일에서는 담기만 남는다(AI 는 하단 고정 바,
뷰 전환은 콘솔 레이아웃이 좁은 화면에 안 맞아 원래 숨는다).

768px 기준으로 제호 우측이 660px → **약 380px**, 액션 줄은 약 280px 이다. 둘 다
한 줄에 여유롭게 들어간다.

콘솔 뷰(2b)의 상단 바도 같은 방식으로 갈랐다. 그쪽은 원래 `flex-wrap` 으로 설계된
바라 증상이 덜했지만, 지수 시세 네 개까지 같은 줄에 있어 결국 같은 문제였다.

```
2a  제호  = 워드마크 · 캡션 · 검색 · 테마 · 계정
2b  상단바 = 워드마크 · QUANT·DESK · 지수 4 · 검색 · 계정
둘 다 액션 줄 = 담기 · 뷰 전환 · AI
```

### 두 토글이 **같은 단어**를 쓰고 있었다

스크린샷에서 계속 나란히 보이던 `TERMINAL` 과 `CONSOLE` 이다. 생김새(mono 대문자
테두리 박스)가 같아 무엇이 색을 바꾸고 무엇이 레이아웃을 바꾸는지 알 수 없었는데,
이유를 보니 어휘가 겹쳐 있었다.

| | 값 | 라벨이 될 수 있는 말 |
|---|---|---|
| 테마 | `editorial` ↔ `terminal` | EDITORIAL · TERMINAL |
| 뷰 | `editorial` ↔ `console` | EDITORIAL · CONSOLE |

**둘 다 `EDITORIAL` 을 표시할 수 있다.** 실제로 그 조합이 되면 같은 글자가 적힌
같은 모양의 버튼 둘이 나란히 선다. 라벨이 상태를 말하는 게 아니라 지워 버린 셈이다.

내부 식별자는 그대로 두고 **테마 라벨만 밝기 언어로** 옮겼다.

```
테마  DARK ↔ LIGHT        (색)        ☾ / ☀
뷰    CONSOLE ↔ EDITORIAL (구조)      ▮ / ▤
```

글리프도 은유를 갈라 놓는다. 라벨을 못 읽는 폭에서도 둘이 **다른 축**이라는 것이
보여야 하고, 해·달과 터미널·기사는 헷갈릴 여지가 없다. `aria-label` 에는 "다크
테마로 전환" · "터미널 콘솔 화면으로" 처럼 축을 밝힌 문장을 따로 둔다 — mono 대문자
약어는 눈으로는 읽히지만 소리로는 안 읽힌다.

### 남은 것

- **아직 아무도 관리자가 아니다.** `ADMIN_EMAILS` 에 본인 이메일을 넣고 로그인하면
  제호 우측에 '관리자' 버튼이 나타난다. 백엔드·프런트의 `ADMIN_API_KEY` 도 같은
  값으로 채워야 한다 — 없으면 화면은 열리고 API 가 503 을 준다(그 안내를
  `AdminUnavailable` 이 상태 코드별로 말한다).
- **AI 사용량은 누적이 아니라 현재 상태다.** 캐시가 프로세스 메모리라 재시작하면
  0 이고 워커가 여럿이면 그중 하나의 숫자다. 누적 집계가 필요하면 그때 저장소를
  만든다 — 지금 필요한 질문("캐시가 일하고 있나")에는 이 값으로 답이 된다.
- 회원 목록에 **페이지네이션이 없다.** 백엔드는 `offset` 을 받지만 화면은 상위
  50명만 그리고 전체 수를 밝힌다. 검색으로 좁히는 편이 빠른 규모다.

그래프 자체는 11회차에서 끝났다(노드 15개, 조건부 엣지·루프 포함). 남겨 둔 것은
**체크포인터** 하나다 — 중단된 실행을 이어받는 기능이고, `advice_graph.py` 주석대로
지금 붙이는 것은 비용만 내는 일이라 의도적으로 보류했다.

⚠️ **붙일 때 아래 두 줄이 예전 안내와 다르다** (15회차에서 바뀜).

- LangGraph 의 `AsyncPostgresSaver` 는 psycopg(v3)로 붙는데, **그 의존성은 지금 없다.**
  10회차에서 추가했던 psycopg·psycopg2 계열을 15회차에서 전부 걷어냈다 — import 되는
  곳이 하나도 없었고, 비바이너리 `psycopg2` 는 리눅스 휠이 없어 slim 이미지 빌드를
  깨뜨리고 있었다. 붙일 때 `psycopg[binary]` 를 **그 이유와 함께** 다시 추가한다.
- 예전 안내는 `core/db_url.to_sync_url()` 로 드라이버에 맞게 바꾸라고 했는데, **그 함수도
  15회차에서 지웠다.** alembic 이 async 엔진으로 옮겨 가면서 부르는 곳이 하나도 없는
  죽은 코드가 됐기 때문이다. 동기 주소가 다시 필요하면 `normalize_url` 옆에 그 소비자와
  함께 되살린다 — git 이력에 원본이 있다.

앱 엔진(asyncpg)과 체크포인터(psycopg)가 **같은 Supabase 를 서로 다른 드라이버로 보게
된다**는 사실 자체는 그대로다. 접속 문자열을 그대로 넘기면 안 된다.

```
      └─────────────┼─────────────┘
                    ▼
              grade_docs  ── 관련성 부족 ──→ rewrite_query ──┐
                    │◄──────────── 최대 2회 루프 ────────────┘

      ▼             ▼             ▼
  저널리스트     경제학자      애널리스트         ← 각자 필요한 문서만 인용
      └─────────────┼─────────────┘
                    ▼
                 decide (구조화 출력)
                    ▼
                 verify  ── 인용 불일치 ──→ decide 재시도 1회 → 규칙 폴백
```

- `langgraph`만 추가하고 **노드 안에서는 기존 `llm.py`를 그대로 쓴다** — "LLM SDK를 import하는
  파일은 하나"라는 원칙을 깨지 않는다.
- 프런트와의 계약인 **SSE 4단계는 유지**한다. 그래프 노드 수가 늘어도 이벤트는 4개다.
- 1단계의 `build_query()`가 그래프의 `rewrite_query` 노드로 승격된다 (지금은 고정 질의).

### 자격 증명 적용 안내 — 구글 OAuth · 메일 (로그인의 마지막 한 칸)

코드는 12회차에 끝났다. 여기 적는 것은 **키를 실제로 꽂을 때 걸리는 것들**이고,
대부분 `.env.local` 두 줄보다 앞에 있는 문제다.

#### 먼저 알아야 할 것 — 키를 넣는 순간 **세션 전략이 바뀐다**

`auth.ts` 는 프로바이더가 하나라도 있을 때만 어댑터를 붙인다.

```
지금 (키 없음)   providers []  →  adapter 없음  →  session: "jwt"
키를 넣은 뒤     providers [1+] →  PostgresAdapter → session: "database"
```

**이 전환이 지금 로그에 쌓이는 `JWTSessionError: no matching decryption secret` 을
없앤다.** 그 에러는 브라우저에 남아 있는 옛 JWT 세션 쿠키를 지금 `AUTH_SECRET` 으로
못 푸는 것인데, DB 전략에서는 쿠키 값을 복호화하지 않고 세션 테이블에서 찾는다.
그래도 깔끔하게 하려면 **접속하는 호스트마다** `authjs.session-token` 쿠키를 한 번씩
지운다 — 쿠키는 호스트별로 따로 산다(`localhost:3000` 과 `192.168.x.x:3000` 이 별개).

전제 하나: `AUTH_DATABASE_URL` 은 백엔드 `DATABASE_URL` 과 **같은 Supabase** 여야 한다.
갈리면 `orphan_service` 가 로그인 사용자의 행을 전부 "소유자 없음" 으로 읽는다(15회차).
NextAuth 테이블 자체는 alembic `b3f1c2d47a90` 이 이미 만들어 뒀으므로 추가 작업이 없다.

#### 구글 OAuth — 함정은 리디렉션 URI 하나다

1. `console.cloud.google.com` → 프로젝트 생성
2. **OAuth 동의 화면을 먼저 만든다.** 이걸 안 만들면 클라이언트 ID 생성 자체가 막힌다.
   - User Type: **External**, 상태는 **Testing** 으로 둔다
   - **테스트 사용자에 본인 구글 계정을 추가한다.** Testing 상태에서는 여기 없는
     계정으로 로그인하면 `403: access_denied` 가 난다 — 키가 틀린 것처럼 보이지만 아니다
   - 스코프는 기본(email · profile)이면 된다. 이 앱은 그 이상 요구하지 않는다
3. 사용자 인증 정보 → OAuth 클라이언트 ID → **웹 애플리케이션**
4. 승인된 리디렉션 URI:

```
http://localhost:3000/api/auth/callback/google
```

> ⚠ **`http://192.168.x.x:3000/...` 은 구글이 받지 않는다.** 구글은 `http` 리디렉션을
> `localhost`(와 `127.0.0.1`)에만 허용하고 사설 IP 는 거부한다. 즉 LAN 주소로 접속한
> 브라우저에서는 **구글 로그인을 쓸 수 없다.** 다른 기기에서도 구글 로그인을 시켜야
> 한다면 https 가 붙은 도메인이 필요하고, 그때까지의 현실적인 우회는 개발용 터널
> (cloudflared·ngrok 등)로 https 주소를 하나 얻어 그것을 리디렉션에 등록하는 것이다.
> 그 경우 `AUTH_URL` 을 그 주소로 함께 고정한다.

```
AUTH_GOOGLE_ID=<클라이언트 ID>
AUTH_GOOGLE_SECRET=<클라이언트 보안 비밀>
```

#### 메일 매직링크 — 함정은 발신 주소다

`EMAIL_SERVER` 는 SMTP URL 이고 `nodemailer` 가 그대로 받는다(이미 의존성에 있다).

```
EMAIL_SERVER=smtp://resend:<API_KEY>@smtp.resend.com:587
EMAIL_FROM=noreply@<검증한 도메인>
```

- **`EMAIL_FROM` 은 그 공급자에서 발송이 허용된 주소여야 한다.** 아무 주소나 적으면
  SMTP 는 붙고 발송만 거부되어, 화면에는 "메일을 보냈습니다" 가 뜨고 메일은 안 온다.
- 도메인이 아직 없으면 Resend 의 `onboarding@resend.dev` 로 시작할 수 있다. 다만
  그때는 **가입한 본인 주소로만** 발송된다 — 혼자 테스트하는 데는 충분하다.
- API 키에 `@`·`/` 같은 문자가 있으면 URL 인코딩한다. 안 하면 호스트 파싱이 깨진다.

#### 어느 것부터 — 구글 먼저를 권한다

매직링크는 도메인 검증까지 가야 반쪽을 벗어나고, 구글은 콘솔 설정만 끝나면 바로
쓸 수 있다. 그리고 **테스트는 `http://localhost:3000` 에서 한다** — 위의 사설 IP
제약 때문에 LAN 주소에서는 구글 버튼이 실패한다.

#### 실제로 넣자마자 터진 것 — `sslmode=require` 가 로그인을 죽인다 (2026-08-10 수정됨)

키를 꽂는 순간 어댑터가 처음으로 **진짜 DB 에 붙는다.** 그때 이게 났다.

```
[auth][error] AdapterError
[auth][cause]: Error: self-signed certificate in certificate chain
```

`lib/auth/pool.ts` 에는 `ssl: { rejectUnauthorized: false }` 가 이미 있었다. 그런데
`pg` 는 접속 문자열을 파싱한 결과로 **호출부가 넘긴 설정을 덮어쓴다.**

```js
// pg/lib/connection-parameters.js
config = Object.assign({}, config, parse(config.connectionString))
```

그리고 `pg-connection-string` 은 `sslmode=require` 를 이렇게 만든다 (실측).

```
?sslmode=require                      →  ssl = {}                          ← 빈 객체
?sslmode=no-verify                    →  ssl = { rejectUnauthorized: false }
?uselibpqcompat=true&sslmode=require  →  ssl = { rejectUnauthorized: false }
(없음)                                 →  ssl = undefined                   ← 우리 설정이 산다
```

**빈 객체가 Node TLS 기본값(검증 켬)이다.** libpq 에서 `require` 는 "암호화하되
검증하지 않음" 인데 이 라이브러리는 더 엄격하게 읽는다 — 같은 실행에서 라이브러리가
스스로 그 사실을 경고로 내고 있었다("'require' 는 'verify-full' 의 별칭으로 취급된다").

그때 그 파일의 주석은 **정반대로, 근거까지 붙여** 적혀 있었다.

> libpq 파라미터(`sslmode`)는 **남긴다** — node-postgres 는 libpq 규약을 따르므로
> 백엔드가 asyncpg 를 위해 떼어냈던 것이 여기서는 오히려 필요하다

규약이 아니라 **구현**이 정하는 문제였다. 13회차의 NULL 정렬(`SQLite 는 NULL 을 가장
작은 값으로 본다`)과 정확히 같은 종류다 — 코드가 틀린 게 아니라 전제가 바뀌었고,
그런 것은 리뷰로 안 잡힌다.

고친 방식은 **백엔드와 같게** 맞추는 것이다. `core/db_url.normalize_url` 이 하는 일을
`toNodePostgresConfig` 가 그대로 한다: libpq 전용 파라미터를 URL 에서 떼고, 그 뜻을
드라이버가 이해하는 형태로 옮겨 담는다. `_tls_for` 의 표도 그대로 옮겼다.

`.env.local` 을 고쳐서(`sslmode=no-verify`) 넘길 수도 있었지만 그러지 않았다 —
문서가 "Supabase URI 를 **그대로** 붙여넣으면 된다" 고 말하고 있고, 그 약속은 코드가
지켜야 한다. 손으로 고치게 하면 다음 사람이 같은 자리에서 다시 막힌다.

덤으로 `sslmode` 가 파서에 닿지 않으므로 그 SECURITY WARNING 도 사라진다.
`pool.test.ts` 가 **라이브러리 동작 자체를** 단언으로 박아 뒀다 — 언젠가 libpq 규약을
따르게 바뀌면 그 테스트가 빨개져서 우회를 걷을 시점을 알려준다.

#### 넣은 뒤 확인할 것 — 승계가 핵심이다

키가 붙으면 `/login` 에 버튼이 나타난다(`AUTH_ENABLED` 가 화면을 가른다).

1. **로그아웃 상태로** 종목 2~3개를 관심종목에 담는다 (익명 `anon:` 쿠키에 붙는다)
2. 로그인한다
3. `/watchlist` 에 그 목록이 **그대로 있는지** 본다 → 승계(`claim.ts`)가 돈 것이다
4. 로그아웃한다. **익명 쪽은 비어 있어야 맞다** — 승계는 복사가 아니라 **이동**이다
5. 못 미더우면 DB 에서 직접 본다

```sql
select owner_key, count(*) from watchlist_items group by 1;
-- 승계 전: anon:<uuid> N건
-- 승계 후: user:<uuid> N건   (anon 행은 사라져 있어야 한다)
```

3번에서 목록이 비어 보이면 `claim.ts` 가 실패를 삼킨 것이다(의도된 동작 — 승계 실패로
화면이 죽지 않는다). 그때는 백엔드 로그에서 `/watchlist/claim` 응답을 본다.

### `listed_companies` 에 컬럼을 더할 때 (16·17회차에서 두 번 했다)

일정 3컬럼(16회차)과 지표 5컬럼(17회차)을 이 절차로 더했다. 다음에도 같다.

- 모델과 마이그레이션을 **같은 커밋**에 두고 `uv run alembic upgrade head` 를 실행한다.
  모델에만 컬럼이 생기면 `listed_companies` 전체 SELECT 가 `UndefinedColumn` 으로 실패해
  **검색·홈·종목 탐색·종목 상세가 동시에** 깨진다. 3회차가 P1 을 미룬 이유가 이것이었다.
- `uv run alembic check` 로 모델과 DB 가 어긋나지 않았는지 확인한다. 15회차부터
  `document_chunks` 까지 포함해 drift 0 이 기준선이다. head 는 **`a4d72f9e51c3`**(리비전 7개).
- 새 컬럼은 대개 **전부 nullable** 이다(배치 전 · 공급자에 없는 종목). 그것으로 정렬한다면
  `nullslast()` 를 명시한다 — 13·14회차의 그 규칙이고, `test_postgres_dialect.py` 의
  검사기가 빠뜨린 자리를 잡는다. **새 읽기 경로는 그 파일의 목록에도 추가한다.**
  안 하면 그 쿼리는 규칙 밖이다 (17회차에 정렬 축 다섯을 전부 목록에 넣었다).
- 인덱스는 **자동이 아니다.** 16회차는 걸고 17회차는 안 걸었다 — 판단 근거는 17회차의
  해당 절에 있다. 요약하면 "조회 형태가 하나로 고정인가" 와 "배치가 그 컬럼을 매일
  전 행 갱신하는가" 를 본다.

**14회차까지 이 자리에 적혀 있던 경고 다섯은 전부 사실이 아니게 됐다**(15회차에서
`db_create_all_on_startup`·인메모리 테스트·`render_as_batch`·`stock.db` 가 모두 사라졌다).
지금 남은 것은 위 넷뿐이다.
